# 단계 5 설계: MTC 기반 Pick-and-Place 통합 작업

## 목표

`pick_and_place_test.launch.py` 한 번의 실행으로 기존 `simulation.launch.py`를 포함해 시뮬레이션과 `pick_and_place_test` 노드를 시작한다. 노드는 준비 상태를 확인한 뒤 Pick-and-Place를 **자동으로 한 번** 수행한다. 팔의 다단계 동작에는 MoveIt Task Constructor(MTC)를 사용하고, 접촉·공 부착/분리·놓기 결과는 Gazebo의 실제 상태로 확인한다. 성공 또는 실패 후에도 작업 노드와 시뮬레이션을 유지해 사용자가 최종 상태를 관찰할 수 있게 한다.

대상은 현재 월드의 고정된 공과 바구니다. 비전, 동적 물체 추적, 실제 RG2 파지력 검증은 포함하지 않는다. 자동 재시도나 두 번째 작업 실행도 하지 않는다. 기존 [MoveIt 적용 계획](../plan/moveit_apply.md)의 단계 5 흐름에, 대화에서 합의한 바구니 안 안정 판정을 완료 조건으로 포함한다. 단계 6에서는 이 판정의 경계값과 실패 사례를 더 폭넓게 통합 검증한다.

## 실행 및 준비 확인

새 launch는 기존 시뮬레이션을 포함하고 작업 노드를 즉시 실행한다. `pick_grasp_test.launch.py`처럼 노드가 준비를 기다리되, 작업 노드는 `spin_once` 대기 루프 대신 `timer_callback`과 비동기 결과로 상태를 전이한다. Launch의 프로세스 시작이나 controller spawner 종료만으로 준비됐다고 판단하지 않는다.

| 필수 준비 조건 | 확인 내용 |
| --- | --- |
| ros2_control | `controller_manager`에서 `joint_state_broadcaster`, `arm_trajectory_controller`, `gripper_trajectory_controller`가 모두 `active`인지 확인 |
| MoveIt | MTC 계획·실행에 필요한 MoveIt 인터페이스와 컨트롤러 액션 경로가 사용 가능한지 확인 |
| 로봇·작업 장면 | 팔 6개·그리퍼 2개 관절의 유효한 최신 상태, Planning Scene의 공(`apple`)·바구니(`basket`), Gazebo의 공 pose·접촉·부착 상태가 사용 가능한지 확인 |

준비 대기 제한의 **초기 제안값은 120초**다. 만료 시 `WAIT_READY`와 충족되지 않은 조건을 `ERROR`로 기록하고 `FAILED_WAITING` 상태로 들어간다. 노드와 시뮬레이션은 유지하고 자동으로 준비 확인을 재시도하거나 작업을 시작하지 않는다. 시간 제한과 각 입력의 최신성 기준은 설정값으로 둔다.

타이머 콜백은 현재 상태와 완료된 비동기 응답을 살펴보고 다음 동작을 **한 번만** 시작한다. 서비스·액션·MTC 계획/실행을 기다리며 콜백을 막지 않는다. MTC API의 계획/실행 호출이 블로킹이면 별도 실행 경로에서 수행하고 타이머에는 결과만 전달한다. 이 실행 경로와 ROS 콜백의 동시 접근은 한 작업만 진행되도록 보호한다. 작업 중 중복 실행 요청은 수용하지 않는다.

## MTC와 Gazebo의 구간별 연결

MTC가 계획한 경로를 물리 확인 없이 끝까지 실행하지 않는다. **MTC 구간 실행 → Gazebo 물리 결과 확인 → Planning Scene 동기화 → 다음 MTC 구간 실행**을 반복한다. 각 새 구간은 직전 실행 후의 관절 상태와 Planning Scene으로 계획한다.

| 순서 | 동작과 담당 | 다음 구간으로 넘어가는 조건 |
| --- | --- | --- |
| 1 | MTC: 그리퍼 열기, 시작 자세, 공 접근 자세를 계획·실행 | 계획·컨트롤러 실행 성공과 최종 관절 상태 확인 |
| 2 | 작업 노드: 그리퍼 닫기 및 Gazebo 접촉 확인 | 기존 단계 4와 같이 접촉 시 닫기 goal의 취소·종료, 두 손가락 실제 관절값과 부착 가능 조건 확인. 접촉이 없으면 부착하지 않음 |
| 3 | 작업 노드: `/grasp/attach` 요청, MoveIt Planning Scene에서 공 부착 | Gazebo 부착 성공과 `/grasp/attached=true` 확인 후 Planning Scene에 attached object 반영·조회 검증 |
| 4 | MTC: 부착된 공을 고려해 들어올리기·바구니 위 이동을 계획·실행 | 각 궤적 결과, 관절 도달, 공의 부착 유지 확인 |
| 5 | 작업 노드: 놓기 위치에서 그리퍼 열기, `/grasp/detach` 요청, Planning Scene 분리 | Gazebo 분리 성공과 `/grasp/attached=false` 확인 후 공을 측정된 월드 pose로 Planning Scene에 반영·조회 검증 |
| 6 | 작업 노드: 바구니 안 안정 판정 | 공 중심 위치와 속도의 연속 안정 조건 충족 |
| 7 | MTC: 후퇴·시작 관절 자세 복귀 | 궤적 실행과 최종 관절 상태 확인 후 `SUCCEEDED_WAITING`으로 전이 |

MTC의 Planning Scene 부착·분리는 Gazebo의 물리 부착·분리를 수행하지 않는다. Gazebo 요청의 성공을 확인한 뒤 MoveIt 장면을 갱신하는 현재 단계 4의 순서를 유지한다. 접촉 반응형 그리퍼 닫기는 기존 단계 4에서 검증한 action 취소·종료와 5° 초과 개방 조건을 보존하며, MTC로 단순히 닫기 궤적 전체를 실행해 접촉 확인을 건너뛰지 않는다. 새 C++ 노드는 기존 Python 도우미의 동기 `spin_once`/`spin_until_future_complete` 호출을 직접 사용하지 않고, 동일한 장면 전환 계약을 비동기로 구현한다.

## 놓기 성공 판정

공 중심이 **바구니 안쪽 영역**에 있으면서 공의 **선속도가 기준 이하**인 상태가 연속 유지될 때만 놓기 성공으로 판단한다. 바구니 입구는 실제 mesh와 월드 pose를 바탕으로 단순한 안쪽 평면 영역으로 근사한다. 경계에서 공 반지름 `0.0325 m`만큼 여유를 두고, 바닥·입구 높이도 확인해 바구니 위 또는 외부에서 정지한 공을 성공으로 오인하지 않는다. 입구의 정확한 치수는 현재 바구니 모델을 확인해 설정값으로 기록한다.

현재 Gazebo 플러그인은 시뮬레이션 시각이 있는 `/grasp/ball_pose`를 발행하고 별도의 속도 토픽은 발행하지 않는다. 초기 구현은 **연속 pose의 거리 ÷ 시뮬레이션 시각 차이**로 선속력을 계산한다. 시각이 증가하지 않거나 pose가 오래됐거나 값이 유효하지 않으면 안정 시간 누적을 중단·초기화한다. 시뮬레이션이 멈춘 시간을 안정 시간에 포함하지 않는다.

| 판정 설정 | 초기 제안값 | 검증 시 확정할 내용 |
| --- | --- | --- |
| 선속력 상한 | `0.02 m/s` | Gazebo 측정 잡음과 정착 동작을 보고 조정 |
| 연속 안정 시간 | 시뮬레이션 시간 `1.0 s` | 위치와 속도 조건을 모두 연속 충족하는지 확인 |
| 안정 판정 최대 대기 | `30 s` | 첫 통합 실행에서 공이 바구니 안으로 들어왔지만 10초 내 연속 안정 시간을 채우지 못해 30초로 늘림. 실제 정착 시간 추가 확인 |
| 바구니 안쪽 영역·높이 | 모델 치수에서 산출 | 공 반지름 여유와 실제 입구·바닥 형상 반영 |

위 시간·속도는 **검증된 값이 아닌 초기 설정 제안**이다. 최대 대기 안에 조건을 충족하지 못하거나 관측값이 유효하지 않으면 `VERIFY_PLACE` 실패로 처리한다. 안정 판정에 성공한 뒤에만 후퇴·복귀한다. 안정 판정 후 공의 최종 pose로 Planning Scene의 월드 object를 갱신한다.

## 실패와 종료 정책

- 준비 시간 초과, MTC 계획 실패, 컨트롤러 실행 실패, 접촉·집기 실패, Gazebo 부착/분리 실패, Planning Scene 불일치, 놓기 실패를 서로 다른 실패 단계로 기록한다.
- 실패 시 단계와 원인, 핵심 측정값을 `ERROR` 레벨로 한 번 남기고 `FAILED_WAITING` 상태에서 현 상태를 유지한다. 특히 그리퍼 닫기 후 접촉이 없으면 부착·자동 복구 동작을 하지 않는다. 진행 중인 액션의 취소·종료 확인처럼 상태를 안전하게 확정하는 절차는 수행한다.
- 실패 후 자동 재시도·후퇴·시작 자세 복귀는 하지 않는다. 성공 후에도 두 번째 작업을 자동으로 시작하지 않는다.
- 새 launch에는 작업 결과에 따른 `Shutdown`을 두지 않는다. 성공·실패 후 작업 노드와 Gazebo·MoveIt·선택적으로 실행한 RViz를 유지한다. 사용자가 launch를 종료하면 진행 중 요청의 취소·정리를 제한된 시간 안에 시도한다.

## 구현 시 확인할 값

1. 설치된 Jazzy MTC의 구간별 계획·실행 API와 필요한 패키지 의존성.
2. 바구니 mesh의 실제 입구 안쪽 치수와 바닥·입구 높이. 현재 월드는 바구니를 `(0.75, 0.25, 0.000022)`에 배치한다.
3. 시작 관절 자세, 공 접근·lift·바구니 위 놓기 자세와 각 구간의 계획·실행 시간 제한. RViz와 실측 시뮬레이션으로 검증한다.
4. 연속 pose로 추정한 속력의 잡음, pose 최신성 기준, 안정 판정 제한 시간을 정상·실패 시나리오에서 조정한다.

## 구현 및 검증 결과 (2026-10-16)

- 설계 범위대로 `pick_and_place_test.launch.py`와 타이머 기반 `pick_and_place_test` 노드를 추가했다. 노드는 준비 상태를 계속 확인하고 한 번 자동 실행하며, 정상·실패 후에도 시뮬레이션을 종료하지 않는다.
- MTC pose 이동은 `GeneratePose → ComputeIK → Connect`로 구성해 가능한 IK 해를 비교하고, lift는 충돌 확인 Cartesian path로 수행한다. 공 접촉/부착/분리/안정성은 Gazebo 상태를 확인한 뒤 Planning Scene에 반영한다.
- action goal 승인 응답이 timeout 뒤늦게 도착하는 경우 해당 goal만 취소하고, 취소 응답과 최종 결과를 callback으로 기록하도록 했다.
- 격리 실행에서 전체 상태가 `APPROACH → CLOSE_CONTACT → ATTACH_SCENE → TRANSPORT → RELEASE → VERIFY_PLACE → REFRESH_SCENE → RETURN → SUCCEEDED_WAITING` 순으로 완료됐다. 최종 반복에서 공의 안정 pose는 `(0.73031, 0.24446, 0.04631) m`, 추정 속력은 `0.00259 m/s`였으며, 성공 이후 노드가 계속 살아 있음을 확인했다.
- 놓기 판정 최대 대기시간은 설정 `30 s`로 둔다. 초기 `10 s` 시험에서 공이 바구니 안에 있었지만 연속 안정 시간 완료 전 timeout 된 사례가 있어 여유를 늘렸다. 재시험에서는 안정 판정에 성공했다.
- 빌드, 대상 테스트(6개 통과), launch Python/YAML 구문 검사 및 `git diff --check`를 통과했다. 계획 실패 및 준비 시간 초과에서도 ERROR 후 대기하는 동작을 확인했다. RViz GUI의 수동 검토와 놓기 경계/미안정 개별 실패 시나리오는 후속 단계에서 계속 검증한다.
- 검증 환경에는 MTC 0.1.8이 기본 설치돼 있지 않아 필요한 Jazzy 패키지를 `/tmp/my_arm_mtc_overlay`에 임시 추출해 빌드·실행했다. 이 임시 overlay는 저장소에 포함하지 않는다. 일반 설치에서는 선언된 package dependencies를 rosdep/apt로 설치해야 한다.
