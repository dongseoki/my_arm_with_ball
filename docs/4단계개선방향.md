# Pick-and-Place 가독성 개선 4단계 진행 방향

- 대상: `my_arm_with_ball_application/src/pick_and_place_test.cpp`
- 목적: 기존 동작을 유지하면서 책임이 명확한 단위로 파일을 점진적으로 분리한다.
- 원칙: 한 번에 한 책임만 옮기고, 매 변경 후 그 변경에 맞는 검증을 한다. 파일 수를 늘리는 것 자체를 목표로 삼지 않는다.

## 진행 순서

### 1. 첫 변경: 실행 진입점 분리

- [x] 완료 (2026-11-15): `main()`을 `pick_and_place_test_main.cpp`로 분리하고 노드 생성 경계를 `pick_and_place_test_node.hpp`로 선언했다. CMake 실행 파일에 두 소스를 등록했다. 패키지 `colcon build` 성공. 실행 테스트·시뮬레이션은 미실행.

`main()`의 ROS 초기화와 executor 실행·종료는 `pick_and_place_test_main.cpp`에 두고, `PickAndPlace` 인스턴스 생성은 `pick_and_place_test_node.hpp`에 선언한 생성 경계를 통해 기존 구현 파일에 위임한다. 클래스 전체나 상태 전환·비동기 작업은 옮기지 않았다.

- 변경 목적: 프로그램 진입점과 노드 구현의 역할을 구분한다.
- 확인: `git diff --check`와 변경 diff를 검토하고 `my_arm_with_ball_application` 패키지의 `colcon build`를 실행한다.
- 이번 범위에서 실행 테스트·시뮬레이션은 하지 않는다. 빌드 결과는 컴파일 확인으로만 기록한다.

### 2. Planning Scene 책임 분리

- [x] 구현 및 컴파일 확인 완료 (2026-11-15). 런타임 기능 검증은 미실행.
- 검증: `colcon build --symlink-install --packages-select my_arm_with_ball_application` 성공, 종료 코드 0, `1 package finished [32.8s]`. 기존 workspace 중복 underlay 경고 외 최종 컴파일·링크 오류 없음.
- 빌드 중 발견한 기존 진입점 중복(`main()` 두 정의 및 노드 생성 함수 누락)은 4.1의 의도대로 기존 구현 파일에 `createPickAndPlaceNode()`를 정의해 정리했다.

사용자 합의에 따라 검증 helper만 추출하는 초기 제안 대신 `PlanningSceneManager` 클래스로 책임을 분리한다.

- `planning_scene_manager.hpp/.cpp`: `scene()`, `apply()`, `sphere()`, `setHandBallCollisionAllowed()`, `verifyScene()`, `syncScene()`을 담당한다.
- `PickAndPlace`: 작업 순서·상태 전환, 관측 및 RobotModel을 이용한 손 변환 계산을 담당한다. 물리 부착·분리는 아래 4.3에서 `GazeboManager`로 위임했다.
- 서비스 클라이언트는 노드가 소유하고, manager에 전달한 호출 함수가 기존 `call()`을 사용한다. 준비 확인·5초 대기·종료 감지·미완료 요청 제거·예외 전달을 복제하지 않는다.
- 공 관측은 기존 순서대로 읽어 인자로 전달한다. 손 변환은 Attach에서만 전달받은 함수로 계산하여 기존 모델 로드·관절 관측 순서를 유지한다.
- Attach/Detach/RefreshWorld 차이, 충돌 행렬과 공-바닥 상시 허용, 공의 소속·형상·위치 검사 및 실패 메시지는 그대로 옮긴다.
- 이번 검증 범위는 사용자 요청대로 application 패키지의 `colcon build`만이다. 단위 테스트·실행 테스트·시뮬레이션은 수행하지 않는다. 컴파일 성공을 기능 검증 완료로 해석하지 않는다.

### 3. MTC 및 Gazebo 책임 분리

- [x] 합의한 메서드 분리 구현 및 컴파일 확인 완료 (2026-11-15).
- 검증: `colcon build --symlink-install --packages-select my_arm_with_ball_application` 성공, 종료 코드 0, `1 package finished [36.3s]`. 기존 workspace 중복 underlay 경고 외 컴파일·링크 오류 없음.
- 사용자 요청대로 단위 테스트·실행 테스트·시뮬레이션은 실행하지 않았다.

| 구성 | 담당 책임 |
|---|---|
| `MtcTaskExecutor` (`mtc_task_executor.hpp/.cpp`) | `configureTask()`, `addJointMove()`, `addPoseMove()`, `executeTask()`, `verifyJoints()` 및 진행 중 계획의 `preempt()` |
| `GazeboManager` (`gazebo_manager.hpp/.cpp`) | `setGazeboAttachment()`, `requireGazeboAttachment()` — 물리 부착·분리 요청 및 최신 관측 확인 |
| `PickAndPlace` | `closeContact()`와 전체 단계별 작업·상태 전환, ROS 인터페이스·관측 소유, 기존 서비스/Action 통신 경로 |

MTC 실행은 executor가 조율하고 Action 송수신·취소 대기는 노드의 `executeMtcSolution()`을 통해 기존 `sendGoal()`·`await()`를 재사용한다. 관절 도달 확인 반복·제한 시간은 executor가 담당하고, 잠금 아래 실제 관절값을 검사하는 함수는 노드가 제공한다. Gazebo 요청과 최신 부착 관측 읽기도 노드가 제공하는 함수를 사용한다. 부착 상태 enum은 `attachment_state.hpp`에서 공통으로 정의해 Gazebo가 Planning Scene 구현에 의존하지 않도록 했다.

노드 종료 시 기존처럼 종료 플래그 설정 → 진행 중 MTC 계획 중단 요청 → 비동기 작업 종료 대기 순서를 유지한다. 관측 잠금·판정식, 목표값·계획 설정, 타임아웃·취소·실패 메시지 및 호출 순서를 보존하도록 옮겼다. 컴파일 성공은 런타임에서의 동작 동일성을 입증하지 않는다.

### 남은 4단계 작업

- 합의한 세 분리 항목(진입점, Planning Scene, MTC/Gazebo)의 **구현 및 컴파일 확인은 모두 완료**했다. 추가 파일·클래스 분리는 현재 필수 작업으로 남기지 않는다.
- 전체 완료 기준 중 **분리 후 런타임 동작 유지 확인**은 남아 있다. 이번 요청에서는 수행하지 않았다.
- **사용자가 새 구조와 분리 이유를 설명할 수 있는지 확인**도 남아 있다. 필요하면 작업 흐름 하나를 따라 클래스 간 호출을 검토한다.
- `transport()`의 단계 전용 직선 상승 Stage 구성과 `closeContact()`는 작업 흐름에 의도적으로 남겨 두었다. 이를 별도 클래스로 더 옮기는 것은 이번 합의 범위가 아닌 선택적 후속 개선이다.

## 매 변경의 진행 절차

1. 옮길 책임과 현재 동작·호출 순서를 확인한다.
2. 필요한 인터페이스와 데이터 소유자를 정한다.
3. 한 책임만 이동하고 기능 변경이나 불필요한 추상화를 섞지 않는다.
4. 변경 diff와 `git diff --check`를 확인한다.
5. 해당 변경에 맞는 빌드·테스트·런타임 검증을 수행하고, 실행하지 않은 검증은 명시한다.
6. 무엇을 옮겼고 왜 이 경계가 적절한지 설명할 수 있는지 확인한 뒤 다음 변경으로 넘어간다.

## 완료 기준

- 각 파일의 책임과 경계가 분명하다.
- 기존 작업 순서와 실패·대기 계약이 유지된다.
- 검증한 항목과 미검증 범위를 구분해 기록한다.
- 사용자가 새 구조와 분리 이유를 설명할 수 있다.

`place_stability.hpp`는 이미 ROS 통신과 분리된 안정성 계산 책임을 가지며 단위 테스트도 있으므로, 이번 단계에서 다시 분리하지 않는다. 기존 동작 보존 기준은 [Pick & Place 검증 범위 정리](pick_and_place_검증범위_정리.md)를 참고한다.
