# 리팩토링 시 활용할 점검 방법

이 문서는 프로젝트 리팩토링 후 반복할 검증 절차다. 결과를 미리 보장하지 않으며, 실제 실행 결과만 보고서에 기입한다. 이후 skill로 분리할 수 있도록 준비·실행·판정·기록 절차를 구분한다.

## 1. 공통 준비 및 판정

### 환경과 기본 검사
프로젝트 루트에서 환경을 설정한다. ROS/Gazebo 작업이 겹치지 않게 각 launch 검사는 하나씩, 새 시뮬레이션으로 진행한다.

```bash
cd /home/dslee/workspace/my_arm_with_ball
source /opt/ros/jazzy/setup.bash
export GZ_VERSION=harmonic
export ROS_DOMAIN_ID=93 GZ_PARTITION=refactor_check
```

`ROS_DOMAIN_ID`와 `GZ_PARTITION`은 예시다. 사용 중인 값이면 다른 값으로 바꾸고, 해당 검사의 모든 터미널에서 동일하게 사용한다.

```bash
colcon build --symlink-install
source install/setup.bash
colcon test
colcon test-result --verbose
```

- 빌드 합격: 명령 종료 코드 0, 빌드 실패 패키지 없음.
- 테스트 합격: `colcon test-result --verbose`에서 errors/failures 0건. skip 및 미등록 검사는 별도 기재한다.
- `colcon test`는 등록된 테스트만 실행한다. lint가 등록되어 있는지 확인하고 빠져 있으면 따로 실행한다.
- 런타임 합격은 각 시험의 명시된 성공 로그·상태값을 기준으로 한다. 노드가 살아 있거나 창이 열렸다는 사실만으로 합격 처리하지 않는다.

### 로그 파일 규칙
검사 실행마다 `./verify/log/`에 독립 로그를 만든다. 파일명은 공백 없는 snake_case 시험명과 실행 시각을 사용한다.

```text
verify/log/<test_name_언더바연결>_<YYYYMMDD>_<HHMMSS>.log
예: verify/log/pick_grasp_test_headless_20261018_140240.log
```

PTY 입력이나 Ctrl+C 종료까지 남겨야 하는 검사는 `script`로 실행해 터미널 출력과 종료 상태를 함께 기록한다. `script -e`는 자식 명령의 종료 상태를 반환한다.

```bash
mkdir -p verify/log
test_name=simulation_launch_headless
log="verify/log/${test_name}_$(date +%Y%m%d_%H%M%S).log"
script -q -e -c 'ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=true rviz:=false' "$log"
```

- `test_name`은 검사별로 바꾼다(예: `colcon_build_symlink_install`, `keyboard_joint_teleop_pty`, `validate_planning`). 같은 초에 중복될 가능성이 있으면 이름을 더 구체화하거나 시각을 다시 생성한다.
- 여러 명령이 한 검사에 속하면 셸 명령 전체를 `script -q -e -c '...' "$log"`로 감싸고, 실행 전에 필요한 ROS 환경을 source한다.
- 로그에 비밀정보·불필요한 개인 데이터가 포함되지 않도록 확인한다. 실패 로그도 삭제하지 말고 보고서에서 참조한다.

### 종료 동작 판정
- 시험 성공 여부는 먼저 기능 성공 로그·상태·validator 종료 코드로 판정한다. 자동 종료 메시지의 종료 코드는 기능 성공 로그를 대체하지 않는다.
- **자동 launch 종료 과정**에서 Gazebo가 SIGSEGV(-11)로 끝나거나 MoveGroup이 SIGINT 후 timeout되어 SIGTERM(-15)으로 종료되는 알려진 현상은, 그 전에 시험 성공 기준을 충족했다면 기능 실패로 보지 않고 정상적인 종료 패턴으로 분류한다. 발생한 프로세스·시그널은 보고서 비고와 로그에 기록한다.
- 위 두 패턴은 자동 종료 중에만 적용한다. 테스트 도중의 SIGSEGV/예외, 성공 로그 부재, 다른 프로세스의 비정상 종료는 실패 또는 추가 확인으로 기록한다.
- 사람이 Ctrl+C로 중단한 경우 자동 종료와 구분하여 기록한다. Ctrl+C 이전 기능 결과를 판정하고, 종료 신호·최종 종료 코드는 별도 비고로 남긴다.
- 테스트 후 내가 시작한 launch/노드가 정리됐는지 확인한다. 다른 작업의 프로세스는 종료하지 않는다.

## 2. AI agent 활용: GUI 없는 검증

### 2-1. simulation.launch.py + keyboard_joint_teleop.py
```bash
ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=true rviz:=false
```
별도 터미널(같은 환경)에서 준비상태를 확인하고, 키보드 노드는 PTY로 실행한다.

```bash
ros2 control list_controllers
ros2 action list -t
ros2 topic echo /joint_states --once
ros2 run my_arm_with_ball_application keyboard_joint_teleop
```

- `joint_state_broadcaster`, `arm_trajectory_controller`, `gripper_trajectory_controller`가 모두 `active`인지 확인한다.
- 팔/그리퍼 `follow_joint_trajectory` action과 최신 팔 6축·손가락 2축 상태를 확인한다.
- 준비 로그 뒤 `1` → `d` → 목표 도달 대기 → `a`를 입력해 ±0.05 rad 움직임을 확인한다.
- `o` → 목표 도달 대기 → `c`로 빈손 그리퍼가 각각 1.18 → 0 rad에 도달하는지 확인한다.
- 액션 성공뿐 아니라 `/joint_states` 목표 오차가 0.01 rad 이내인지 확인한다. `r`은 선택 축, `x`는 팔 전체를 0 rad로 재설정한다(`x`는 초기자세와 같다고 가정하지 않는다).
- 동작 중 일반 키 입력은 무시되고 재생되지 않아야 한다. `q`와 Ctrl+C는 종료 입력이다. Ctrl+C 시험은 취소 완료와 터미널 복구까지 확인한다.
- PTY 입력을 실행하지 못했다면 키보드 통합은 미확인이다. 단위 테스트로 대체 판정하지 않는다.

### 2-2. pick_grasp_test.launch.py: 집기·분리 자동 시험
```bash
ros2 launch my_arm_with_ball_bringup pick_grasp_test.launch.py headless:=true rviz:=false
```
빈손 attach 거부 → 공 접촉·부착 → 상승 시 공 추종 → detach 후 낙하를 검사한다. 합격 로그는 `STAGE4 GRASP TEST PASSED`다. 바구니 운반 시험은 아니다. 종료 패턴은 공통 종료 판정에 따른다.

### 2-3. pick_and_place_test.launch.py: 집기·운반·놓기 자동 시험
```bash
ros2 launch my_arm_with_ball_bringup pick_and_place_test.launch.py headless:=true rviz:=false
```
공 집기 → 상승·운반 → 바구니 내 안정 확인 → 후퇴·시작 관절 복귀를 검사한다. 합격 로그는 `STAGE5 PICK AND PLACE PASSED; waiting`이다. 성공 후 대기하므로 로그를 확인하고 Ctrl+C로 종료하며, 수동 종료 코드로 기능 성공/실패를 판단하지 않는다. `STAGE5 FAILED`는 실패 로그다. 안정 조건은 `my_arm_with_ball_application/config/pick_and_place_test.yaml`을 따른다.

### 2-4. demo.launch.py: 독립 계획 전용 시험
```bash
ros2 launch my_arm_with_ball_moveit_config demo.launch.py use_rviz:=false
# 별도 터미널에서
ros2 run my_arm_with_ball_moveit_config validate_planning.py
```
validator 종료 코드 0, home 유효, 접근·상승·바구니 위 계획 성공, 공/바구니 충돌 음성 대조군 거부가 합격 기준이다. Gazebo나 궤적 실행 검증은 아니다. simulation과 동시에 같은 ROS domain에서 실행하지 않는다.

### 2-5. 보조 launch 범위
- `move_group.launch.py`는 MoveGroup 구성 요소이며 기본 실행은 비활성화되어 있다. demo 시험에서 함께 검증한다.
- `moveit_rviz.launch.py`는 RViz 전용이고 headless 옵션이 없다. 사람 확인에서 검증한다.
- 두 launch는 로봇 상태·TF·장면을 독립 제공하지 않으므로 각 파일만 단독 실행해 통합 성공으로 판정하지 않는다.

## 3. 사람 확인: GUI 검증

한 번에 하나씩 실행한다. 자동 시험 중에는 키보드 노드로 중복 제어하지 않는다.

```bash
ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=false rviz:=true
# simulation 실행 중 별도 터미널에서
ros2 run my_arm_with_ball_application keyboard_joint_teleop
# 앞 시험을 종료한 뒤 각각 실행
ros2 launch my_arm_with_ball_bringup pick_grasp_test.launch.py headless:=false rviz:=true
ros2 launch my_arm_with_ball_bringup pick_and_place_test.launch.py headless:=false rviz:=true
ros2 launch my_arm_with_ball_moveit_config demo.launch.py use_rviz:=true
```

- simulation: 로봇·공·바구니 표시, RViz TF/모델 오류, Gazebo와 RViz의 관절 자세 일치를 확인한다.
- 키보드: `1`~`6`, `a/d`, `r/x`, `o/c`를 동작 완료를 기다리며 입력하고 방향·대칭·떨림·관통을 살핀다.
- grasp: 공의 손 추종 상승·분리 후 낙하, RViz의 부착/월드 객체 전환을 확인한다.
- pick-and-place: 공이 바구니 안에 안정적으로 남고 팔이 복귀하는지 본다. Stage 5 성공 로그도 확인한다.
- demo: 로봇·장면 표시와 `ur5` 그룹의 Plan 경로를 확인한다. 계획 전용이므로 Execute 성공은 요구하지 않는다.
- GUI 관찰 결과는 자동 로그 판정과 분리해 기록한다. Headless 성공만으로 시각·접촉 품질까지 통과 처리하지 않는다.

## 4. 점검 보고서 작성 템플릿

점검 파일은 `verify/verify_result_YYYY-MM-DD_HHMMSS.md`로 저장한다. 시작 시각, 환경, 실행한 로그 파일 경로와 미실행 항목을 함께 쓴다. 검사별 상태는 `성공`, `실패`, `미확인`, `해당 없음` 중 하나만 사용한다. 전체 판정은 검사별 결과를 요약해 `전체 성공`, `일부 성공`, `실패`, `판정 보류` 중 선택한다.

```markdown
# 점검 결과 (YYYY-MM-DD HH:MM:SS KST)

- 대상/변경 요약:
- 실행 환경: ROS 배포판, Gazebo 버전, ROS_DOMAIN_ID/GZ_PARTITION
- 전체 판정: 전체 성공 / 일부 성공 / 실패 / 판정 보류
- 실행하지 못한 검사와 이유:

| 점검 항목 | 결과(성공/실패/미확인/해당 없음) | 비고 |
|---|---|---|
| 빌드 |  | 명령, 종료 코드, 실패 패키지 |
| colcon 테스트 및 lint |  | 테스트 수, failure/error/skip, 미등록 검사 |
| simulation + controller/joint states |  | 활성 controller, action, 상태 최신성 |
| keyboard teleop PTY |  | 키 입력, 목표 오차, 종료/터미널 복구 |
| pick_grasp 자동 시험 |  | 성공 로그, 종료 시그널 패턴 |
| pick-and-place 자동 시험 |  | 성공/실패 로그, timeout 및 종료 패턴 |
| demo planning validator |  | 종료 코드, 계획·충돌 대조 결과 |
| GUI 사람 확인 |  | 화면/접촉 결과 또는 미확인 사유 |

## 로그 파일
- `verify/log/<test_name>_<YYYYMMDD>_<HHMMSS>.log`:

## 발견 사항 / 후속 조치
- 정상 종료 패턴으로 분류한 SIGSEGV 또는 SIGTERM은 해당 단계와 성공 기준 충족 여부를 비고에 명시한다.
- 기능 실패, 조사할 종료 현상, 재검증 항목을 구분한다.
```

보고서 표의 각 검사항목은 실행한 경우 반드시 상태를 채운다. 정상 종료 패턴에 해당해 기능 실패로 보지 않더라도 로그와 비고를 생략하지 않는다.
