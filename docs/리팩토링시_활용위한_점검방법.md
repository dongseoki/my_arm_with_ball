# 리팩토링 시 활용할 점검 방법

이 문서는 검증 절차이며, 통과 결과를 의미하지 않는다. 프로젝트 루트에서 실행한다.

## 1. 공통 사항
- 변경 전·후 같은 조건으로 검사하고, 기존 실패와 새로 발생한 실패를 구분한다.
- 모든 실행 터미널에 아래 환경을 적용한다. 테스트는 하나씩, 매번 새 시뮬레이션으로 실행한다.
```bash
cd /home/dslee/workspace/my_arm_with_ball
source /opt/ros/jazzy/setup.bash
export GZ_VERSION=harmonic
export ROS_DOMAIN_ID=93 GZ_PARTITION=refactor_check
```
- 위 domain/partition은 예시다. 사용 중이면 다른 값으로 바꾸되 관련 터미널은 동일하게 맞춘다.
- 빌드·테스트 후, 별도 실행 터미널에서도 `source install/setup.bash`를 적용한다.
```bash
colcon build --symlink-install
source install/setup.bash
colcon test
colcon test-result --verbose
```
- 합격: 빌드 성공, 등록된 테스트의 실패·오류 0건. skip/미등록 검사는 별도 기록한다.
- `colcon test`는 등록된 테스트만 실행한다. lint 등록 여부를 확인하고 누락 시 별도 수행한다.
- 각 시험의 명령·변경 전후 결과·로그·종료 코드·미확인 항목을 남긴다.
- 실행 중 fatal/예외/timeout을 확인한다. 프로세스가 살아 있거나 창이 뜨는 것만으로 합격하지 않는다.
- 완료 후 해당 시험의 노드·launch를 Ctrl+C로 종료한다. 다른 작업의 프로세스는 종료하지 않는다.

## 2. AI agent 활용: GUI 없이 검증
### 2-1. simulation.launch.py + keyboard_joint_teleop.py
```bash
ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=true rviz:=false
```
- 별도 터미널에서 준비 상태를 확인한다.
```bash
ros2 control list_controllers
ros2 action list -t
ros2 topic echo /joint_states --once
ros2 run my_arm_with_ball_application keyboard_joint_teleop
```
- `joint_state_broadcaster`, `arm_trajectory_controller`, `gripper_trajectory_controller`가 모두 `active`여야 한다.
- 팔·그리퍼의 `follow_joint_trajectory` 액션과 최신 팔 6축·손가락 2축 상태를 확인한다.
- 키보드 노드는 PTY(가상 터미널)로 실행하고 입력한다. 파이프 입력은 TTY 검사 때문에 사용할 수 없다.
- 준비 로그 후 `1` → `d` → 완료 대기 → `a`를 입력한다. 시작 상태 대비 ±0.05 rad 이동을 확인한다.
- `o` → 완료 대기 → `c`: 손가락 두 축이 각각 1.18 → 0 rad에 도달하는지 확인한다(빈손 기준).
- 액션 성공뿐 아니라 `/joint_states`가 목표 오차 0.01 rad 이내인지 확인한다.
- `r`은 선택 축, `x`는 팔 전체를 0 rad로 만든다. `x`가 시뮬레이션 초기 자세와 같다고 가정하지 않는다.
- 동작 중 일반 키 추가 입력은 무시되고 이후 재생되지 않아야 한다. `q`/Ctrl+C는 종료 예외다.
- 동작 중 Ctrl+C도 별도 시험하여 취소·종료 및 터미널 복구를 확인한다.
- PTY 입력을 못 했다면 키보드 통합 시험은 미확인으로 남긴다. 단위 테스트로 대체 판정하지 않는다.

### 2-2. pick_grasp_test.launch.py: 집기·분리 자동 시험
```bash
ros2 launch my_arm_with_ball_bringup pick_grasp_test.launch.py headless:=true rviz:=false
```
- 빈손 attach 거부 → 공 접촉·부착 → 상승 시 공 추종 → detach 후 낙하를 검사한다.
- 합격: `STAGE4 GRASP TEST PASSED` 출력 및 launch 자동 종료 코드 0. 바구니 운반은 검사하지 않는다.

### 2-3. pick_and_place_test.launch.py: 집기·운반·놓기 자동 시험
```bash
ros2 launch my_arm_with_ball_bringup pick_and_place_test.launch.py headless:=true rviz:=false
```
- 공 집기 → 상승·운반 → 바구니에 놓기·안정 확인 → 후퇴·시작 관절 복귀를 확인한다.
- 합격: `STAGE5 PICK AND PLACE PASSED; waiting`. 성공 후에도 대기하므로 로그 확인 후 Ctrl+C로 종료한다.
- `STAGE5 FAILED`는 실패 후 대기 상태다. 프로세스 생존/수동 종료 코드로 성공 판정하지 않는다.
- 안정 판정 범위·속도·시간은 `my_arm_with_ball_application/config/pick_and_place_test.yaml`을 기준으로 한다.

### 2-4. demo.launch.py: 독립적인 계획 전용 시험
```bash
ros2 launch my_arm_with_ball_moveit_config demo.launch.py use_rviz:=false
# 별도 터미널에서 실행
ros2 run my_arm_with_ball_moveit_config validate_planning.py
```
- 합격: validator 종료 코드 0, home 유효, 접근·상승·바구니 위 계획 성공, 공/바구니 충돌 음성 대조군 거부.
- Gazebo 및 trajectory 실행 시험이 아니다. simulation과 같은 domain에서 동시에 실행하지 않는다.

### 2-5. 보조 launch 범위
- `move_group.launch.py`: GUI 없는 MoveGroup 구성 요소. 기본은 실행 비활성화이며 2-4에서 함께 검증한다.
- `moveit_rviz.launch.py`: RViz 전용이며 GUI 끄기 옵션이 없다. headless 대상에서 제외하고 3절에서 검증한다.
- 두 파일은 로봇 상태·TF·장면까지 제공하는 독립 시험 환경이 아니므로 `demo.launch.py`를 통해 검사한다.

## 3. 사람 확인: GUI로 검증
- 아래 명령은 하나씩 실행한다. 자동 시험 실행 중에는 키보드 노드로 중복 제어하지 않는다.
```bash
ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=false rviz:=true
# 위 simulation 실행 시에만 별도 터미널에서 실행
ros2 run my_arm_with_ball_application keyboard_joint_teleop
# 앞 시험 종료 후 각각 실행
ros2 launch my_arm_with_ball_bringup pick_grasp_test.launch.py headless:=false rviz:=true
ros2 launch my_arm_with_ball_bringup pick_and_place_test.launch.py headless:=false rviz:=true
ros2 launch my_arm_with_ball_moveit_config demo.launch.py use_rviz:=true
```
- simulation: 로봇·공·바구니 표시, RViz TF/모델 오류 유무, Gazebo와 RViz의 실제 관절 자세 일치를 확인한다.
- 키보드: `1`~`6` 선택 후 `a/d`, `r/x`, `o/c`를 완료 대기하며 검사한다. 방향·대칭·떨림·관통을 관찰한다.
- grasp: 공이 손을 따라 상승하고 분리 후 떨어지는지, RViz 부착/월드 객체 전환이 맞는지 확인한다.
- pick-and-place: 공이 바구니 안에 안정적으로 남고 팔이 복귀하는지 확인한다. 2-3 성공 로그도 필요하다.
- demo: 로봇·장면 표시와 `ur5` 그룹의 Plan 경로를 확인한다. 계획 전용이므로 Execute 성공은 요구하지 않는다.
- GUI 관찰과 자동 로그 판정을 따로 기록한다. Headless 성공만으로 시각·접촉 품질까지 통과 처리하지 않는다.
