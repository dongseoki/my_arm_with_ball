# 3단계 구현 설명: MoveIt 궤적 실행과 키보드 팔 조작

## 목적

3단계에서는 MoveIt이 계획한 팔 궤적을 Gazebo 시뮬레이션의 로봇에 전달해 실행할 수 있도록 연결했다. 키보드 조작도 기존 위치 명령 토픽 대신 같은 팔 궤적 액션 인터페이스를 사용한다. 이 단계는 **팔의 MoveIt 궤적 실행과 키보드 조작 연결**까지를 완료 범위로 한다.

## 동작 구조

```text
MoveIt (경로 계획·실행 요청) ─┐
                              ├─ FollowJointTrajectory 액션
키보드 노드 (상대 목표 계산) ─┘              ↓
                                  arm_trajectory_controller
                                              ↓
                                      Gazebo의 UR5 팔
                                              ↓
                              joint_state_broadcaster → /joint_states
```

MoveIt과 키보드 노드는 서로 다른 목적지 생성 경로를 사용하지만 팔을 움직이는 실행 통로는 공유한다.

- **MoveIt 경로:** MoveIt이 현재 상태와 장면을 바탕으로 궤적을 계획하고 실행한다. 실행기는 설정된 시작 상태 허용 오차를 확인한 뒤 컨트롤러 액션에 궤적을 보낸다.
- **키보드 경로:** 키보드 노드가 `/joint_states`에서 관절 상태를 읽어 짧은 목표 궤적을 만들고 컨트롤러 액션에 직접 보낸다. 이 경로는 MoveIt의 경로 계획 및 충돌 검사를 거치지 않는다.
- `/joint_states`는 실제 Gazebo 관절 상태를 보고하는 피드백 경로이며, 액션 성공 결과와 함께 목표 도달 여부를 확인하는 데 사용한다.

## 컨트롤러와 MoveIt 연결

팔 6축의 기존 위치 명령 컨트롤러를 제거하고 `joint_trajectory_controller/JointTrajectoryController`인 `arm_trajectory_controller`로 교체했다. 이 컨트롤러는 `/arm_trajectory_controller/follow_joint_trajectory`의 `control_msgs/action/FollowJointTrajectory` 액션을 제공한다. 팔 관절의 position 명령 인터페이스는 이 컨트롤러만 점유하도록 해 같은 관절에 대한 중복 명령 경로를 두지 않는다.

MoveIt 설정의 Simple Controller Manager에는 팔 컨트롤러 이름, 액션 namespace, 6개 팔 관절을 등록했다. 여기서 말하는 **MoveIt Controller Manager**는 MoveIt의 궤적을 어떤 ROS 컨트롤러/액션으로 보낼지 연결하는 MoveIt 측 플러그인이다. Gazebo의 ros2_control `controller_manager`와는 다른 구성요소다. 이번 설정은 MoveIt이 컨트롤러를 직접 켜고 끄지 않고, 활성 컨트롤러의 FollowJointTrajectory 액션으로 궤적을 전달하게 한다.

`simulation.launch.py`는 Gazebo와 MoveIt을 함께 시작한다. 컨트롤러는 `joint_state_broadcaster`가 성공한 뒤 팔 trajectory 컨트롤러, 그리퍼 위치 컨트롤러 순서로 시작하며, 컨트롤러 준비 전 MoveIt 실행이 앞서가지 않도록 통합 실행을 연결한다. `headless:=true`는 Gazebo를 화면 없이 실행하고 `rviz:=false`는 RViz를 끈다.

계획 전용 `demo.launch.py`는 실제 궤적 실행을 비활성화한 채 유지한다. 따라서 MoveIt 실행이 가능한 것은 통합 Gazebo launch 경로이며, 계획 전용 데모가 의도치 않게 시뮬레이터를 제어하지 않는다.

## 키보드 조작

별도 터미널에서 다음 노드를 실행한다.

```bash
ros2 run my_arm_with_ball_application keyboard_joint_teleop
```

키보드 노드는 팔/그리퍼 컨트롤러 활성 상태, FollowJointTrajectory 액션 서버, 신선한 `/joint_states`를 확인한 후 입력을 받는다. 시작 시 자동으로 초기 자세 명령을 보내지 않는다.

| 키 | 동작 |
|---|---|
| `1`–`6` | 선택할 팔 관절 지정 |
| `a` / `d` | 선택 관절을 현재 실제 상태 기준으로 각각 `-0.05` / `+0.05 rad` 이동 |
| `r` | 선택 관절을 `0 rad`로 이동 |
| `x` | 팔 6축을 모두 `0 rad`로 이동; 그리퍼는 움직이지 않음 |
| `o` / `c` | 기존 `gripper_position_controller` 토픽을 이용한 그리퍼 열기/닫기 유지 |

팔 동작은 trajectory action이 진행 중이면 새 팔 입력을 큐에 쌓지 않고 무시하며 로그를 남긴다. 새 목표는 입력 시점의 최신 관절 상태에서 계산한다. 제한 시간은 궤적 시간에 2초 여유를 더해 설정하며, 실제 상태가 목표에서 관절별 0.01 rad 이내인지 확인한다.

상태가 없거나 0.5초보다 오래된 경우, 관절 한계를 벗어나는 목표, 액션 실패 또는 timeout은 오류 로그로 남긴다. 오류는 사용자가 알아보기 쉽도록 한국어와 영어를 함께 포함한다. Timeout이면 진행 중 goal을 취소하고 결과가 확인된 다음 입력을 재개하며, 액션 실패 후에도 키보드 노드는 계속 실행된다. 자동 재시도는 하지 않는다.

## 파라미터와 검증 기준

| 검사 항목 | 기준 |
|---|---:|
| MoveIt 실행 궤적 시작 상태 허용 오차 | `0.02 rad` |
| 키 입력에 사용하는 `/joint_states` 최대 나이 | `0.5 s` |
| `a/d` 한 번의 관절 이동량 | `0.05 rad` |
| 키보드 궤적의 최소 실행 시간 | `1.0 s` |
| 키보드 목표 상태 허용 오차 | 관절별 `0.01 rad` |
| 키보드 action timeout 여유 | 궤적 시간 + `2.0 s` |

이 값들은 서로 다른 검사 지점을 위한 값이다. 예를 들어 MoveIt 시작 상태 허용 오차는 실행 전 계획 궤적과 실제 시작 상태의 차이를 제한하며, 키보드 목표 허용 오차는 실행 후 `/joint_states`와 요청 목표를 비교한다.

## 실행 및 재현

ROS Jazzy 환경을 준비한 뒤 통합 시뮬레이션을 실행한다.

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
ros2 launch my_arm_with_ball_bringup simulation.launch.py headless:=true rviz:=false
```

실제 화면에서 확인할 때는 `headless:=true rviz:=false`를 생략하거나 `rviz:=true`로 실행한다. 통합 launch가 준비된 후 별도 터미널에서 키보드 노드를 실행한다. 컨트롤러와 액션 상태를 확인할 때는 다음 명령을 쓸 수 있다.

```bash
ros2 control list_controllers
ros2 control list_hardware_interfaces
ros2 action list | grep follow_joint_trajectory
ros2 topic echo /joint_states
```

각 검증 단계는 빈 작업 공간에서 작은 안전한 팔 이동으로 시작한다. 키보드 직접 액션은 MoveIt 충돌 검사를 우회하므로 공이나 바구니에 접근하는 용도로 사용하지 않는다.

## 구현 및 시험 결과

2026-10-13 기준 구현 및 검증 결과:

- `colcon build --symlink-install` 성공, workspace 5개 패키지 빌드.
- `colcon test` 및 `colcon test-result --verbose` 성공: 테스트 스위트 3개, 실패 0개.
- Headless 통합 실행에서 `joint_state_broadcaster`, `arm_trajectory_controller`, `gripper_position_controller`가 모두 활성 상태였고, 팔 6축 명령 인터페이스를 trajectory 컨트롤러가 점유했다. 기존 팔 위치 컨트롤러는 실행되지 않았다.
- MoveIt의 짧은 팔 경로 실행이 성공했고 `/joint_states`에서 관절 이동을 확인했다. 시작 상태 허용 오차를 넘는 시험 궤적은 거부됐다.
- 키보드 동작 경로의 `+0.05 rad` 요청에서 관측된 최종 관절 위치는 약 `0.045 rad`였고 목표와의 오차 약 `0.005 rad`로 `0.01 rad` 허용 범위 안이었다.
- 계획 전용 데모에서는 trajectory 실행이 비활성화되고 `/execute_trajectory` 액션이 제공되지 않는 것을 확인했다.
- 실행 환경에 GUI 표시 장치가 없어 RViz의 시각 확인은 수행하지 않았다.

전체 작업 기록과 상세 설계 기준은 [`m_3_plan.md`](../plan/m_3_plan.md), 단계별 적용 추적은 [`moveit_apply.md`](../plan/moveit_apply.md)를 참고한다.

## 이번 단계에서 제외된 항목

- MoveIt gripper controller/action과 `gripper` group 실행 연결. 그리퍼 `o/c`는 기존 토픽 제어를 유지한다.
- Gazebo 접촉 감지, 공 부착/분리, 파지 성공 판단 및 Pick-and-Place 전체 시퀀스.
- 키보드의 직접 액션 경로에 MoveIt 경로 계획이나 충돌 검사를 추가하는 작업.
- GUI/RViz를 통한 시각적 검증.

그리퍼를 MoveIt에서 직접 실행하는 연결은 별도 후속 작업으로 남겨두며, 접촉 및 부착 동작보다 먼저 다룬다.
