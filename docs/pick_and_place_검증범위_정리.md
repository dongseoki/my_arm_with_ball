# Pick & Place 보존 기준과 기존 검증 범위

- 작성일: 2026-11-15
- 대상: `my_arm_with_ball_application/src/pick_and_place_test.cpp`
- 이번 작업: 보존 기준 10개 연결, 기존 테스트 내용의 정적 검토, 추가 관찰 시나리오 정의
- 하지 않은 작업: 빌드·테스트·시뮬레이션 실행, 새 테스트 구현, 소스·설정 변경

## 1. 결론과 검증 수준

사용자가 충분하다고 판단한 [리팩토링 시 활용할 점검 방법](리팩토링시_활용위한_점검방법.md)을 기본 검증 절차로 유지한다. 모든 예외 경로를 자동화하거나 완전한 테스트 커버리지를 확보하는 것은 이번 목표가 아니다.

기존 문서에는 정상 동작의 실행 방법, 판정, 기록 절차가 이미 있다. 새 검증 체계를 만들기보다 아래에서 보존 기준과의 관계를 정리하고, 직접 검사하지 않는 부분을 명시한다. 예외 시나리오는 선택적 보완안이며 기존 점검의 필수 범위를 늘리지 않는다.

이 문서에서 “검사한다”는 테스트 코드에 해당 검사가 있다는 뜻이다. 이번 실행에서 통과했거나 동작을 완전히 보장한다는 뜻은 아니다.

## 2. 보존 기준 10개와 기존 검사의 연결

아래 절 번호는 기존 점검 문서를 기준으로 한다. 소스 검토는 실행 테스트와 별도 근거다.

| 번호 | 보존 기준 | 기존 검사·확인 방법 | 확인 범위와 남는 한계 |
|---|---|---|---|
| 1 | 준비되면 자동으로 한 번만 실행 | §2-3 Stage 5의 시작·상태·성공 로그 확인. `tick()`의 시작 및 terminal-state 분기 검토 | 정상 실행 시작은 확인 가능. 성공 후 장시간 재실행하지 않는지는 기존 절차에 관찰 시간 기준이 없다. |
| 2 | 단계 순서 유지 | §2-3에서 `STAGE5 state=` 로그 순서와 성공 로그 확인. `tick()` 상태 전환 비교 | 정상 경로의 순서를 확인할 수 있다. 모든 실패 위치의 전환을 검사하는 테스트는 아니다. |
| 3 | 준비 미완료 재확인 및 시간 초과 후 대기 | §2-1은 준비된 controller/action/joint state 확인. `readiness()`와 `tick()`의 WAIT_READY 처리 검토 | §2-1은 Stage 5 준비 실패 시험이 아니다. C++ 준비 시간 초과 후 대기는 별도 실행 시나리오가 없다. |
| 4 | 작업 실패 시 단계·이유 기록 후 대기 | §2-3은 `STAGE5 FAILED`를 실패 로그로 정의. `fail()`과 `tick()`의 예외 처리 검토 | 실패 로그 판정 기준은 있지만 작업 실패를 의도적으로 유발하는 절차는 없다. |
| 5 | 실패 후 자동 재시도·복귀·노드 종료 없음 | `fail()` 및 `tick()`의 FAILED_WAITING 조기 반환 검토 | 정상 성공 시험만으로 실패 후 행동을 직접 확인하지 못한다. 취소 미확정 시 이미 진행 중인 동작이 즉시 정지한다고 보장하는 계약과는 다르다. |
| 6 | 시작 관절 복귀 후 성공 대기 | §2-3의 복귀·성공 로그, §3 GUI 관찰. RETURN의 `executeTask()`와 `verifyJoints()` 검토 | 정상 복귀 경로에서 관절 도달 검증을 거친다. 대기 지속 관찰 시간은 별도로 정해져 있지 않다. |
| 7 | Gazebo 부착과 MoveIt 장면 반영을 각각 확인 | §2-2 집기·분리 시험, §2-3 C++ 실행, §3 GUI 관찰. `requireAttachment()`·`trigger()`·`syncScene()`·`verifyScene()` 검토 | Stage 5 정상 경로는 C++ 내부 검사들을 거친다. Stage 4/Python 단위 테스트가 C++ 구현을 직접 검사하는 것은 아니다. |
| 8 | 최신 관측·바구니 범위·속도·연속 안정 시간 | `test_place_stability.cpp`, §2-3, pose 콜백과 `waitForStablePlacement()` 검토 | 계산 로직과 정상 놓기 경로를 검사한다. 오래된 관측 처리와 VERIFY_PLACE 시간 초과 전환의 전용 노드 테스트는 없다. |
| 9 | 목표값·속도·타임아웃·취소·도달 조건 유지 | §1 빌드·등록 테스트와 §2-3 실행에 더해 C++·YAML·launch의 변경 전후 diff 비교 | 정상 성공은 모든 수치 불변·시간 초과·취소 분기를 증명하지 않는다. 조건 유지에는 코드/설정 비교를 함께 사용한다. |
| 10 | 작업과 콜백 처리 분리, 단계 순차 실행 | §2-3 정상 동작, `std::async(std::launch::async)`·Future 확인·구독 콜백·executor 구성의 변경 전후 비교 | 정상 실행은 실용적인 회귀 근거다. 데이터 경합이나 모든 스케줄링을 검증하는 동시성 테스트는 아니다. |

정상 경로의 기대 로그 순서:

```text
WAIT_READY → APPROACH → CLOSE_CONTACT → ATTACH_SCENE → TRANSPORT
→ RELEASE → VERIFY_PLACE → REFRESH_SCENE → RETURN → SUCCEEDED_WAITING
```

로그 이름은 C++ `stateName()` 기준이다. 최초 WAIT_READY는 생성자의 준비 대기 로그로 나타난다. 성공 판정은 기존 문서처럼 `STAGE5 PICK AND PLACE PASSED; waiting`을 사용하며, 로그만으로 GUI 접촉 품질을 확인했다고 기록하지 않는다.

lint는 정적 품질 검사이며 기능 검증의 대체가 아니다. 판정·기록은 기존 점검 문서의 lint 참고 항목 정책을 유지한다.

### 3-2. 런타임 검사

- **simulation + keyboard PTY (§2-1):** 제어 기반과 사용자 입력 흐름 확인. C++ PickAndPlace 전체 검사가 아니다.
- **pick_grasp (§2-2):** 빈손 부착 거부, 접촉 집기, 부착 후 추종, 분리 후 낙하 확인. Python Stage 4 경로이며 바구니 운반 시험은 아니다.
- **pick-and-place (§2-3):** C++ 노드의 실제 정상 집기·운반·놓기·복귀 경로를 확인하는 핵심 통합 검사다. 내부 관절·부착·장면·안정성 검사 실패는 성공 로그까지 도달하지 못하게 한다.
- **demo validator (§2-4):** 계획 가능성과 충돌 음성 대조 확인. Gazebo 물리 실행은 확인하지 않는다.
- **GUI (§3):** 모델·자세·물체 추종·놓기 등을 사람이 관찰한다. headless 성공으로 대체 판정하지 않는다.

실행 절차를 나열한 문서와 실행 결과는 다르다. 변경 전 기준 결과는 이후 별도 실행 로그와 보고서로 확보해야 한다.

## 4. 예외 경로 보완에 필요한 조치 — 정의만, 선택 사항

내가 제안한 보완은 예외 처리 코드를 새로 넣자는 뜻이 아니라, **일부 조건을 의도적으로 미충족시킨 뒤 기존 실패 처리와 대기 동작을 관찰하자**는 의미였다. 이번에는 아래 시나리오 정의만 수행한다. 기본 검증 절차로 충분하다는 사용자 판단을 유지하며, 아래를 리팩터링 진행의 추가 필수 관문으로 삼지 않는다.

관찰 5초, 준비 제한 3초 등의 값은 시험 시간을 줄이기 위한 제안값이지 기존 제품 요구사항이 아니다. 유한한 관찰은 그 시간 동안의 동작만 확인한다.

### A. 성공 후 대기 관찰

- 방법: 기존 Stage 5 정상 시험에서 성공 로그 직후 종료하지 않고, 예를 들어 5초 동안 노드 생존과 새 시작·상태 로그 발생 여부를 관찰한다.
- 기대: 성공 후 새로운 자동 작업이 시작되지 않고 노드가 유지된다.
- 근거: 성공 로그 시각, 관찰 종료 시각, 그 사이 로그와 노드 생존 기록.
- 한계: “영원히 재실행하지 않는다”는 증명은 아니다. 새 동작이나 노드 종료가 보이면 실패다.

### B. 준비 시간 초과 후 실패 대기

- 방법: 다른 작업과 격리된 ROS domain에서 시뮬레이션 없이 이 노드만 실행하여 관측 미수신 상태를 만든다. 준비 제한 시간을 임시 실행 인자로 예를 들어 3초로 설정한다. 저장소 YAML은 수정하지 않는다.
- 기대: 준비 중에는 APPROACH로 진행하지 않고, 이후 `STAGE5 FAILED stage=WAIT_READY reason=Preparation timed out: ...`가 기록된다. 그 후 예를 들어 5초 동안 노드가 살아 있고 재시작·복귀하지 않는다.
- 근거: 시작·실패 로그와 시각, 실패 후 노드 생존 및 새 작업 로그 부재.
- 한계: 생성자 설정 오류 등으로 WAIT_READY 진입 전에 종료하면 이 시나리오를 확인한 것이 아니다. 모든 서비스·컨트롤러 미준비 사유를 각각 검사하는 시나리오도 아니다.

### C. 놓기 확인 실패 후 대기

- 방법: 별도의 새 시뮬레이션에서 이동 목표는 유지하고, 안정 판정에만 쓰는 `basket_bounds`를 실제 공이 들어가지 않는 유효한 범위로 임시 지정한다. 예: 각 축 범위를 10~11 m로 지정. 테스트용 파라미터 사본/override는 저장소의 기본 설정과 분리한다.
- 기대: RELEASE 이후 VERIFY_PLACE까지 도달한 뒤 제한 시간 초과로 실패한다. 이후 REFRESH_SCENE·RETURN·성공으로 진행하지 않고 노드가 대기한다.
- 근거: VERIFY_PLACE 및 해당 단계 실패 로그, 실패 후 관찰 구간의 노드 생존과 후속 작업 부재.
- 한계: 앞 단계에서 실패하면 VERIFY_PLACE 실패 경로를 확인한 것이 아니다. 이 경로는 `waitForStablePlacement()`의 직접 `fail()` 호출을 확인하며, Future 예외 재전달이나 MTC 취소 확인을 검사하지 않는다.

### 이번 수준에서 추가 구현하지 않는 것

- 일반 작업의 모든 예외 종류를 강제로 발생시키는 mock/fault-injection 기반 C++ 테스트
- MTC goal 승인 지연·취소 거부·최종 결과 미확정 등의 세부 경합 자동화
- 전체 동시성·입력 경계 조합의 완전한 검사

해당 경로는 이번에 완전히 검증됐다고 주장하지 않는다. 관련 코드를 실제로 변경하거나 문제를 발견할 때 필요한 범위만 다시 판단한다. 선택 시나리오를 나중에 실행한다면 기존 점검 문서의 격리·순차 실행·본인이 시작한 프로세스만 정리하는 원칙을 그대로 따른다.
