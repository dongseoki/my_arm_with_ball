# MoveIt 적용 단계 3 질의응답

이 문서는 [`plan/moveit_apply.md`](../plan/moveit_apply.md)의 단계 3을 시작하기 전에 필요한 개념과 선택지를 현재 저장소 기준으로 설명한다. 결론부터 말하면, 팔은 `joint_trajectory_controller`의 `FollowJointTrajectory` 액션으로 연결하는 전환안을 권한다. 별도의 중간 변환 노드를 새로 만드는 것보다 MoveIt 실행 경로가 단순하고, 목표 시각을 포함한 궤적 실행 결과를 확인하기 쉽기 때문이다. 단, 기존 키보드 조작 경로는 새 액션 컨트롤러에 맞춰 조정하거나 별도 호환 동작을 마련해야 한다.

## 1. Joint trajectory 액션 인터페이스란?

**관절 궤적(joint trajectory)**은 로봇 관절 하나의 목표값이 아니라, 여러 관절의 목표값을 시간 순서대로 묶은 경로다. 각 지점에는 보통 관절 이름, 위치(필요하면 속도·가속도), 그리고 시작 후 몇 초에 도달할지를 나타내는 시간이 들어간다. 예를 들어 “0.5초 뒤 어깨 관절을 A 위치로, 1.2초 뒤 팔꿈치를 B 위치로”처럼 전달한다. MoveIt은 경로를 계획하지만, 실제 관절을 시간에 맞춰 움직이는 일은 컨트롤러가 맡는다.

ROS 2의 `FollowJointTrajectory`는 이 궤적을 **액션(action)**으로 보내는 표준적인 요청/응답 방식이다. 클라이언트(MoveIt)가 궤적 목표를 보내면 서버(팔 컨트롤러)는 수락/거부를 알리고 실행 중 상태를 제공하며, 끝나면 성공·실패 결과를 돌려준다. 취소도 요청할 수 있다. 따라서 단순히 목표값을 한 번 발행하는 토픽보다 진행 중 상태와 완료 여부를 다루기에 적합하다.

현재 팔의 `arm_position_controller`는 `ForwardCommandController`다. 이 컨트롤러는 `/arm_position_controller/commands` 토픽으로 6개 위치 명령값을 받지만, 시간 지점이 여럿인 궤적을 실행하는 `FollowJointTrajectory` 액션 서버는 제공하지 않는다. 즉 MoveIt이 계산한 시간 기반 궤적을 그대로 넘길 인터페이스가 아직 없다. 그리퍼도 현재는 별도의 `ForwardCommandController`다.

## 2. 전환안과 호환 경로 비교

| 선택 | 구성 | 장점 | 단점·주의점 |
|---|---|---|---|
| **A. 컨트롤러 전환 (권장)** | 팔의 `ForwardCommandController`를 `joint_trajectory_controller/JointTrajectoryController`로 바꾸고, MoveIt이 해당 컨트롤러의 `FollowJointTrajectory` 액션을 호출 | MoveIt 표준 실행 경로와 직접 연결된다. 궤적의 시간 지점, 진행 상태, 완료/실패 결과를 컨트롤러가 처리한다. 중간 변환 코드가 적어 디버깅 경계가 명확하다. | 기존 키보드 노드는 현재 `Float64MultiArray` 토픽을 쓰므로 그대로는 팔을 조작하지 못한다. 키보드도 액션을 호출하도록 바꾸거나, 별도 수동 조작 경로를 정해야 한다. 동일 관절을 두 컨트롤러가 동시에 제어하지 않도록 활성 컨트롤러를 관리해야 한다. |
| **B. 호환 경로(변환 노드)** | 현재 위치 명령 컨트롤러를 유지하고, MoveIt 궤적 액션을 받아 지점별 위치 명령으로 바꾸어 발행하는 어댑터/브리지 노드를 추가 | 기존 키보드 토픽과 컨트롤러를 유지할 수 있어 전환 초기 변경량이 작아 보일 수 있다. 기존 제어 경로를 점진적으로 보존할 수 있다. | 변환 노드가 궤적 시각, 보간, 취소, timeout, 중간 실패, 액션 결과를 직접 구현해야 한다. 단순히 각 지점 값을 토픽으로 발행하면 속도·시간 특성이 달라질 수 있고, MoveIt에는 실행이 끝났는지 정확히 알려야 한다. 자체 코드와 시험 범위가 늘어난다. |

**이 저장소에서 A가 더 나은 이유:** 현재 MoveIt 계획 설정은 이미 있지만 실행은 의도적으로 꺼져 있고, MoveIt controller 설정도 비어 있다. 반면 Gazebo 쪽에는 `gz_ros2_control` 및 ros2_control 구성이 있으며 팔 명령은 단일 `ForwardCommandController`에 집중되어 있다. 그러므로 팔에 표준 trajectory 컨트롤러를 추가/교체하고 MoveIt controller 설정에서 그 액션을 가리키는 편이 책임 경계가 분명하다. B는 기존 키보드 토픽을 그대로 보존해야 한다는 요구가 강할 때 고려할 수 있지만, 현재 단계의 목표인 MoveIt 실행 검증에는 불필요한 실행 어댑터를 추가한다.

권장 범위는 **팔 6축을 먼저 trajectory 액션으로 검증하고, 그리퍼는 별도 제어 경로로 남기는 것**이다. 그리퍼 집기 동작은 이후 단계에서 별도로 다룬다. 기존 키보드 제어를 계속 쓸 필요가 있다면, 새 액션 컨트롤러를 기본으로 두고 키보드 노드가 같은 액션을 호출하도록 변경하는 것이 가장 일관적이다. 두 컨트롤러를 같은 팔 관절에 동시에 활성화하는 방식은 피해야 한다.

## 3. MoveIt controller manager란?

이 이름은 두 층을 가리킬 수 있어 구분이 중요하다.

1. **MoveIt의 controller manager 플러그인**은 MoveIt 안에서 “어떤 관절 그룹을 어떤 ROS 컨트롤러/액션으로 실행할지” 알려주는 연결 어댑터다. 저장소의 `my_arm_with_ball_moveit_config/config/moveit_controllers.yaml`에는 현재 `MoveItSimpleControllerManager` 종류만 선언되어 있고, 실행용 컨트롤러/action endpoint는 아직 설정되어 있지 않다.
2. **ros2_control의 `controller_manager`**는 Gazebo 안의 하드웨어 인터페이스를 통해 실제 관절 명령을 실행하는 쪽이다. 저장소의 `my_arm_with_ball_bringup/config/ros2_controllers.yaml`은 여기에 상태 발행기와 팔·그리퍼 컨트롤러 종류를 등록한다. 보통 `ros2 control list_controllers`로 상태를 확인하는 대상이다.

간단히 말하면 MoveIt 쪽은 **어디로 보낼지 선택/연결**하고, ros2_control 쪽은 **관절에 명령을 적용**한다. 둘 다 controller manager라고 불리지만 같은 노드나 같은 역할이 아니다. `MoveItSimpleControllerManager` 자체가 Gazebo를 제어하는 것도 아니다.

## 4. “저위험 단일 관절/짧은 경로부터 실행”의 의미

계획 결과를 곧바로 긴 pick-and-place 작업 전체에 실행하지 말고, 실패 영향과 확인 난도가 작은 순서로 실행하자는 뜻이다.

1. **연결만 확인:** Gazebo에서 trajectory 컨트롤러가 `active`인지, `FollowJointTrajectory` 액션 서버가 보이는지, MoveIt이 올바른 관절 이름으로 목표를 보낼 수 있는지 확인한다. 이때는 실행을 아직 하지 않아도 된다.
2. **단일 관절의 아주 작은 이동:** 팔이 안전하고 간섭이 없는 시작 자세에 있는지 확인한 뒤, 예를 들어 한 관절만 현재값에서 약 `0.02`~`0.05 rad` 이동하고 되돌리는 짧은 궤적을 보낸다. 나머지 관절은 현재 위치를 유지한다. 값은 실제 모델 한계·환경에 맞춰 더 작게 정할 수 있다. 실행 전후 `/joint_states`와 RViz/Gazebo 표시를 비교하고, 액션이 성공으로 끝나는지도 확인한다.
3. **짧은 다관절 경로:** 작은 단일 관절 동작이 정상일 때만 충돌 여유가 있는 짧은 팔 경로를 실행한다. 계획 시작 상태와 실제 Gazebo 상태가 맞는지, 실행 중 관절 상태가 따라오는지, 끝 상태 오차와 timeout/거부 처리가 적절한지 본다.
4. **그 다음에 작업 포즈 경로:** 짧은 경로의 실행과 상태 동기화가 확인된 후에야 공 접근·lift 등 더 큰 동작으로 확장한다. 이 단계는 공 부착/분리나 전체 자동 pick-and-place 검증을 뜻하지 않는다.

“저위험”은 안전이 자동 보장된다는 뜻이 아니다. Gazebo는 시뮬레이터지만 잘못된 큰 목표는 모델을 급격히 움직이거나 충돌시킬 수 있다. 따라서 시작 자세, 관절 한계, 충돌 상태, 명령 관절 목록을 먼저 확인하고 작은 목표부터 진행한다. 단일 관절 시험은 우선 **팔 trajectory 실행 연결과 상태 추종**을 확인하는 시험이지, 공을 집는 시험이 아니다.

## 5. 현재 저장소에서 확인되는 사실과 단계 3의 판단

- 팔과 그리퍼는 현재 각각 `ForwardCommandController`이고, 팔은 6개 관절 위치값 토픽, 그리퍼는 2개 관절 위치값 토픽으로 제어된다: [`ros2_controllers.yaml`](../my_arm_with_ball_bringup/config/ros2_controllers.yaml).
- MoveIt의 컨트롤러 YAML에는 실행 endpoint가 없고, 계획 전용 MoveGroup은 trajectory 실행을 비활성화한다: [`moveit_controllers.yaml`](../my_arm_with_ball_moveit_config/config/moveit_controllers.yaml), [`move_group.launch.py`](../my_arm_with_ball_moveit_config/launch/move_group.launch.py).
- 키보드 노드는 기존 컨트롤러의 토픽 제어를 사용하므로 trajectory 컨트롤러 전환 시 조정이 필요하다: [`keyboard_joint_teleop.py`](../my_arm_with_ball_application/scripts/keyboard_joint_teleop.py).
- 따라서 단계 3의 권장 순서는 팔 컨트롤러/action endpoint 구성 → MoveIt controller 매핑 및 실행 허용 → 키보드 제어 호환 방식 결정/적용 → 관절 상태 동기화 확인 → 단일 관절의 작은 궤적 → 짧은 다관절 궤적이다. 그리퍼와 물체 집기 기능은 이 시험에 섞지 않는다.

### 용어 한 줄 정리

- **계획(planning):** MoveIt이 충돌을 피하는 관절 경로를 계산한다.
- **궤적 실행(trajectory execution):** 시간 정보가 있는 경로를 컨트롤러에 보내 로봇을 실제로 움직인다.
- **FollowJointTrajectory 액션:** 궤적 실행을 요청하고 진행/성공/실패 결과를 받는 표준 ROS 2 통신 인터페이스다.
- **MoveIt controller manager:** MoveIt의 계획 결과를 어느 실행 컨트롤러로 보낼지 연결한다.
- **ros2_control controller manager:** 실행 컨트롤러를 관리하고 시뮬레이터/하드웨어 관절 인터페이스와 연결한다.
