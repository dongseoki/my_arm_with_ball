# pick_and_place_test.cpp 가독성 개선 방향

- 작성일: 2026-11-12
- 대상: `my_arm_with_ball_application/src/pick_and_place_test.cpp`
- 성격: 현재 코드를 정적으로 검토한 개선 제안. 구현 변경을 완료했다는 의미가 아니다.
- 범위: 기존 동작을 유지하면서 사용자가 이해하고 수정하기 쉬운 구조로 개선하기

## 1. 결론

파일을 분리하는 방향은 좋다. 다만 **긴 파일을 여러 개로 나누기보다 작업 순서와 구현 세부사항을 구분하는 것**이 먼저다.

목표는 줄 수 감소가 아니라 다음과 같다.

> 작업 순서는 한곳에서 읽히고, 자세한 구현은 궁금할 때만 찾아볼 수 있으며, 사용자가 동작을 설명하고 수정할 수 있는 코드.

전체 줄 수가 크게 줄지 않아도 이 기준을 충족하면 성공한 리팩터링이다.

## 2. 현재 코드가 읽기 어려운 이유

검토 시점의 파일은 1,571줄이며, 하나의 `PickAndPlace` 클래스에 여러 책임이 모여 있다.

| 책임 | 현재 구현 예 |
|---|---|
| 설정 읽기·검증, ROS 인터페이스 생성 | 생성자 |
| 서비스·Action 대기와 취소 | `await()`, `sendGoal()`, `call()` |
| MoveIt Planning Scene 관리 | `touchAllowed()`, `verifyScene()`, `syncScene()` |
| MTC 구성·계획·실행 | `configureTask()`, `addPoseMove()`, `executeTask()` |
| 실제 작업 단계 | `approach()`, `closeContact()`, `transport()`, `release()` |
| 상태 전환·비동기 작업 관리 | `tick()` |

핵심 문제는 서로 다른 책임이 한 파일 안에서 같은 수준으로 보인다는 점이다. 공을 어떻게 옮기는지 이해하려다가 Action 취소, mutex, 장면 메시지 처리까지 함께 읽게 된다.

반대로 `approach()`는 비교적 좋은 형태다. 본문만 읽어도 다음 순서가 드러난다.

> 접촉 허용 → 그리퍼 열기 → 시작 자세 → 준비 자세 → 접근 → 실행

따라서 전부 새로 만들기보다, 이미 읽기 좋은 부분의 스타일을 나머지에 확장하는 방식이 적합하다.

## 3. 권장 진행 순서

### 1단계: 작업 흐름을 자기 말로 정리한다

먼저 코드를 바꾸지 않고 다음 흐름을 이해한다.

> 준비 확인 → 접근 → 접촉하며 닫기 → 부착 장면 반영 → 운반 → 놓기 → 안정 확인 → 장면 갱신 → 복귀

각 단계에서 다음 세 가지를 설명할 수 있도록 한다.

1. 무엇을 하는가?
2. 무엇을 확인해야 다음 단계로 가는가?
3. 실패하면 어떻게 되는가?

**완료 기준:** 함수 이름을 외우는 것이 아니라, 작업 흐름과 각 확인 절차가 필요한 이유를 설명할 수 있다.

### 2단계: 변경하면 안 되는 동작을 고정한다

가독성 개선과 기능 변경을 동시에 하면 문제 발생 시 원인을 구분하기 어렵다. 이번 리팩터링에서는 다음 동작을 유지한다.

- 자동으로 한 번만 실행한다.
- 단계와 실행 순서를 유지한다.
- 접촉·부착·관절 도달·놓기 안정성 확인을 유지한다.
- 타임아웃과 Action 취소 처리를 유지한다.
- 성공·실패 후 대기하고 자동 재시도하지 않는다.
- Gazebo의 물리 상태와 MoveIt Planning Scene 상태를 따로 확인한다.

현재 CMake에는 `PlaceStability` 단위 테스트가 등록되어 있다. 하지만 이것만으로 전체 상태 전환과 취소 동작이 보장되는 것은 아니다.

변경 전에 정상 실행의 기준을 확보하고, 필요한 실패 경로의 회귀 테스트를 보강한다. 검증 결과는 다음을 구분해서 판단한다.

- MTC 계획 성공
- 컨트롤러를 통한 실행과 관절 도달
- Gazebo에서의 실제 접촉·부착·분리
- MoveIt Planning Scene 반영
- 바구니 안에서의 안정성 확인

**완료 기준:** 보존할 동작과 검증 방법이 명확하고, 변경 전 기준 결과가 확보되어 있다.

### 3단계: 한 파일 안에서 읽는 순서를 개선한다

큰 설계 변경보다 작은 개선부터 진행한다.

- 생성자의 설정 처리와 ROS 인터페이스 생성을 이름 있는 함수로 구분한다.
- `tick()` 안의 복귀 작업을 `returnToStart()` 같은 함수로 추출한다.
- 상태 전환 처리와 단계 실행 분배를 구분한다.
- `trigger(bool)`, `syncScene(bool, bool)`처럼 호출만 보면 뜻이 모호한 인터페이스의 개선을 검토한다.

예를 들어 `syncScene(false, true)`는 함수 정의를 찾아야 의미를 알 수 있다. 이런 부분에서는 파일 수보다 함수 이름과 인자의 의미가 가독성에 더 큰 영향을 준다.

단, 비동기 처리나 잠금 범위까지 한꺼번에 바꾸지는 않는다. `VERIFY_PLACE`의 폴링은 `waitForStablePlacement()`라는 별도 책임으로 유지한다.

**완료 기준:** 상위 흐름을 읽을 때 세부 구현을 계속 오가지 않아도 된다.

### 4단계: 책임이 드러난 뒤 파일을 하나씩 분리한다

한 덩어리씩 옮기고, 매번 빌드와 관련 테스트를 확인한다. 전체를 한 번에 재작성하는 방식은 피한다.

AI가 새 구조를 한꺼번에 만들면, 사용자가 다시 이해해야 하는 문제가 반복될 수 있다. 각 변경에서 무엇을 옮겼고 왜 옮겼는지 설명할 수 있는 크기로 진행한다.

**완료 기준:** 분리한 책임이 명확하고 기존 동작이 유지되며, 사용자가 새 구조를 설명할 수 있다.

## 4. 파일 분리의 권장 책임 경계

다음은 목표로 삼을 책임 구분이며, 확정된 파일명이나 클래스 설계는 아니다.

| 구성 | 담당 역할 |
|---|---|
| 실행 진입점 | ROS 초기화, 노드 생성, executor 실행 |
| 작업 진행 노드 | 상태 전환, 단계 순서, 성공·실패 처리 |
| MTC 관련 구현 | Stage 구성, 계획, 실행, 최종 관절 검증 |
| Planning Scene 관련 구현 | 충돌 허용, 부착·분리 반영, 장면 검증 |
| 그리퍼·Gazebo 관련 구현 | 접촉 닫기, 물리 부착·분리 요청과 확인 |
| 기존 `place_stability.hpp` | 놓인 공의 안정성 계산 |

### 처음부터 클래스를 많이 만들 필요는 없다

위 표는 곧바로 클래스를 여섯 개 만들자는 뜻이 아니다. 처음에는 같은 클래스의 구현을 책임별 `.cpp`로 나누는 중간 단계도 가능하다. 이후 공유 데이터와 소유권이 명확해진 부분만 별도 클래스로 분리한다.

파일 수를 늘리는 것 자체가 목적이 되어서는 안 된다. 분리 후에도 모든 파일이 같은 내부 상태에 강하게 의존한다면 책임 분리는 아직 충분하지 않은 것이다.

### 파일 분리와 ROS 노드 분리는 다르다

이번 목표는 가독성 개선이다. 여러 ROS 노드로 나눠 통신과 실행 관리까지 복잡하게 만들 필요는 없다.

### 기존 PlaceStability를 참고한다

`place_stability.hpp`는 ROS 통신 없이 입력값으로 안정성을 계산한다. 역할이 명확하고 단독 테스트가 가능하다는 점에서 좋은 분리 사례다.

## 5. 주석 정리 방향

현재 긴 분량에는 상세한 한국어 설명과 Doxygen도 포함되어 있다. 길다는 이유로 주석부터 삭제하지 않는다.

장기적으로는 다음처럼 역할을 구분한다.

| 위치 | 담을 내용 |
|---|---|
| 함수 이름 | 무슨 일을 하는지 |
| 코드 주석·Doxygen | 왜 필요한지, 좌표계·단위, 실패 조건, 주의할 계약 |
| 필요에 따른 별도 학습 설명 | API 한 줄씩의 상세한 사용법 |

특히 `transport()`의 공과 손 위치 차이 보정처럼 물리적인 이유가 있는 설명은 유지할 가치가 크다. 사용자의 이해에 필요한 설명은 일괄적으로 제거하지 않는다.

## 6. 가장 먼저 할 작업

추천하는 첫 변경 단위는 다음과 같다.

> 현재 작업 흐름을 이해하고 보존할 동작과 검증 기준을 정한 뒤, `tick()`과 생성자를 읽기 쉽게 정리하는 작은 리팩터링.

그다음 Planning Scene처럼 책임이 비교적 뚜렷한 부분을 분리하고, 마지막에 MTC와 그리퍼 관련 구조를 다듬는다.

진행 원칙은 다음과 같다.

1. 기존 동작을 먼저 확인한다.
2. 한 번에 하나의 책임만 정리한다.
3. 변경한 부분을 검증한다.
4. 사용자가 변경 이유와 동작을 이해한 상태에서 다음 부분으로 넘어간다.

- 파일 분리의 정확한 인터페이스와 클래스 소유권은 실제 리팩터링 전에 추가로 설계해야 한다.
