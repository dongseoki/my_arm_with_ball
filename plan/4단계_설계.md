# MoveIt 적용 4단계 설계 — 그리퍼 접촉·공 부착/분리

## 1. 목표

Gazebo 시뮬레이션에서 RG2 그리퍼가 공과 접촉했는지 확인하고, 접촉 및 그리퍼 닫힘 조건을 모두 만족할 때만 공을 그리퍼에 부착한다. 부착된 공은 로봇 팔을 조금 들어 올릴 때 손을 따라 움직여야 하며, 분리 요청 뒤에는 Gazebo 물리에 따라 낙하해야 한다. 각 부착/분리 전환은 MoveIt Planning Scene에도 반영해 두 상태가 일치하도록 한다.

이번 단계는 전체 공 운반이나 바구니에 놓는 Pick-and-Place 작업 노드를 만들지 않는다. 시험은 기존 월드의 공을 대상으로 `접근 → 닫기 → 부착 확인 → 조금 들어 올려 동반 이동 확인 → 열기/분리 → 낙하 확인`까지 수행한다. 바구니에 넣기와 놓기 성공 판정은 후속 단계 범위다.

기준선으로 팔·그리퍼를 MoveIt에서 실행하는 통합 Gazebo launch가 있고, RViz 실행은 선택 가능하다(`simulation.launch.py`, `rviz` 인자). 기존 Planning Scene 로더는 월드 프레임의 `apple` 충돌 물체를 등록한다(`planning_scene_loader.cpp`). 반면 현재 계획 문서에는 Gazebo 접촉 감지와 공 부착/분리가 아직 없다고 기록돼 있다(`moveit_apply.md`, 단계 4).

## 2. 완료 기준

| ID | 완료 기준 | 확인 방법 |
|---|---|---|
| AC-1 | 그리퍼 두 finger joint 상태로부터 전체 개방 각도를 일관된 단위·방향으로 산출하며, 5° 경계 비교가 명시적으로 정의되어 있다. | 판정 로직 단위 테스트: 경계 미만/같음/초과, 양 관절 방향 및 유효하지 않은 상태값 검사 |
| AC-2 | Gazebo에서 손가락과 공의 접촉 정보를 안정적으로 읽을 수 있고, 접촉하지 않은 상태와 구분된다. | 실행 중 접촉 시작·해제 시 상태 확인, 센서/상태 스트림 준비 및 timeout 오류 확인 |
| AC-3 | 접촉과 닫힘 조건을 모두 만족할 때만 공을 부착한다. 둘 중 하나라도 만족하지 않으면 부착하지 않고 실패/미충족 결과를 알린다. | 빈손 닫기 및 접촉 없는 닫기 음성 시험, 조건 충족 시험 |
| AC-4 | 부착 시 Gazebo 공이 `rg2_hand` 기준으로 그리퍼를 따라가며, 분리 후에는 독립 동역학 물체로 낙하한다. | Gazebo 통합 시험에서 부착 전후 공 pose 비교, 소량 lift 동반 이동, 분리 후 낙하 관찰 |
| AC-5 | 부착 중 MoveIt Planning Scene에서 공은 월드 물체가 아니라 그리퍼에 부착된 물체로 표현되고, 분리 후에는 월드 물체로 복귀한다. 두 전환 모두 장면 반영 완료를 확인할 수 있다. | Planning Scene 상태 조회 및 부착/분리 직후 Gazebo 공 상태와 대조 |
| AC-6 | 테스트용 launch가 기존 Gazebo·MoveIt 통합 구성을 재사용하고, 선택적으로 RViz를 띄운다. 준비가 끝난 뒤 집기 시험을 실행하며 실패 시 비성공 결과를 반환한다. | 헤드리스 자동 시험 및 RViz 시각 확인 가능한 launch 실행; 준비 timeout/시험 실패 검증 |
| AC-7 | 단위 검사와 Gazebo 통합 시험을 구분해 실행할 수 있고, 전체 바구니 운반은 시험 범위에 포함되지 않는다. | 관련 패키지 빌드·테스트와 통합 시나리오 실행; 문서화된 실행 명령 및 결과 확인 |

성공 판정은 빈손에서는 공이 붙지 않고, 실제 접촉과 닫힘 조건을 만족하면 붙어 들어 올릴 때 따라오며, 분리하면 떨어지고, MoveIt 장면도 해당 상태와 일치하는 것이다. 물리적 파지력·마찰·미끄러짐 성능은 성공 조건이 아니다.

## 4. 구현 순서

1. **현재 인터페이스와 모델 기준 확인**: RG2 두 finger joint의 값·방향·개방각 정의, 실제 Gazebo entity/model/link 이름, 로봇 링크에서 접촉 정보를 받을 수 있는 방법, 현재 설치된 Gazebo Harmonic/ROS 연동 방식을 확인한다. 공의 월드 충돌 물체 ID는 `apple`이며, 초기 위치는 `apple_pick_place.sdf`와 Planning Scene 로더에서 대조한다.
2. **접촉 및 부착 방식의 작은 기술 검증**: 사용할 Gazebo 접촉 관측 방식과 물리적으로 공을 붙였다 떼는 방식을 후보 비교 후 최소 실험으로 입증한다. 접촉 미검출, 중복 부착, 존재하지 않는 공 요청의 오류 동작도 확인한다. 여기서는 방식이 확정되기 전부터 새 의존성이나 런타임 구조를 넓히지 않는다.
3. **상태/요청 경계와 Planning Scene 전환 설계**: `detached → attached → detached` 상태 전이, 접촉 및 5° 조건, attach/detach 요청·결과·timeout을 정의한다. Gazebo 전환이 성공한 뒤에만 MoveIt 장면 변경을 확정하고, 한쪽만 성공했을 때의 실패/복구 처리를 명시한다. `rg2_hand`는 기존 계획에서 end-effector 링크로 정해져 있다.
4. **기능 및 단위 검사 구현**: 접촉 상태, 개방각 조건, 단일 공 상태 전이와 오류 처리를 구현하고 독립 단위 검사를 통과시킨다.
5. **테스트용 launch와 시험 구동부 구현**: 기존 `simulation.launch.py`를 재사용해 준비 완료 후 시험을 시작한다. 기본 launch의 기존 활용을 깨지 않으며 RViz는 선택적으로 켠다. 테스트 구동부는 전체 이송이 아니라 합의된 짧은 집기/분리 시나리오만 포함한다.
6. **Gazebo + MoveIt 통합 검증**: 빈손/비접촉 음성 경우, 접촉·닫힘 조건 충족, 공 동반 lift, 분리 후 낙하 및 Planning Scene 동기화를 헤드리스로 재현한다. RViz 실행도 별도로 열어 상태 확인이 가능한지 점검한다. 실패는 종료 상태와 로그로 식별 가능해야 한다.
7. **회귀 검증 및 결과 기록**: 관련 패키지 빌드·테스트·lint를 실행하고 일반 simulation launch 및 계획 전용 MoveIt 데모에 영향이 없는지 확인한다. 실행 명령, 예상 결과, 측정 결과, 미실행 GUI 검증을 문서화하고 상위 단계 계획을 갱신한다.

## 5. 설계 제약 및 구현 시 결정 사항

- 공과 바구니 위치는 기존 SDF 월드의 고정 좌표를 사용한다. 바구니 안에 넣기나 안정 판정은 이 단계에서 구현하지 않는다.
- 로봇 팔/그리퍼 이동은 기존 MoveIt 실행 연결을 사용한다. 키보드 teleop은 이 시험의 제어 주체가 아니며, 그리퍼 실행 경로를 중복 제어하지 않는다.
- ROS 2의 관절 상태는 라디안이므로, 문서의 5° 기준은 비교 전 라디안으로 명시 변환한다. “전체 개방 각도”를 두 관절값에서 산출하는 식과 부호/방향은 URDF 및 실측으로 확인해 시험 결과에 기록한다.
- 접촉 sensor topic/state source, Gazebo attach/detach API 경계, 동기화 노드가 서비스인지 action인지, 재시도·timeout 및 양 시스템 전환 불일치 처리 방식은 1~3단계 조사 결과로 정한다. 설계 단계에서는 구체 API 이름을 미리 고정하지 않는다.
- 짧은 lift 목표와 허용 오차, 접촉 안정 시간, 상태 응답 timeout은 실제 모델·실행으로 안전한 값을 확인해 설정한다. 이 값들은 시험에서 관찰한 로그와 함께 고정한다.
- Planning Scene은 붙은 동안 `apple` 월드 객체를 제거하고 동일한 충돌 형상을 `rg2_hand`에 부착하며, 분리 후 월드 객체로 되돌려야 한다. 초기 등록 로더(`planning_scene_loader.cpp`)와 이 전환의 시작/완료 순서 및 객체 pose를 일관되게 처리한다.
- 부착/분리 전환이 Gazebo와 MoveIt 중 하나에서 실패하면 시험을 성공으로 처리하지 않는다. 안전하지 않은 상태를 로그로 드러내고 다음 단계로 진행하지 않는다.
- 검증은 시뮬레이션 기능 및 소프트웨어 상태 일치에 대한 것이다. 실제 로봇, 실제 파지력, 마찰 모델의 신뢰성은 보증하지 않는다.

## 6. 검증 명령 및 기대 증거

구현 시 현재 환경과 의존성에 맞춰 명령을 확정하되, 최소한 아래 검증을 수행한다.

1. `colcon build --symlink-install`로 변경된 패키지 및 의존 패키지 빌드.
2. 변경 패키지 선택 실행을 포함한 `colcon test`와 `colcon test-result --verbose`; 결과에서 실패 0 확인.
3. 테스트용 launch를 headless 모드로 실행하고 시험 프로세스의 종료 코드, 단계 로그, Gazebo 공 상태 및 Planning Scene의 apple world/attached 상태 변화를 확인.
4. 실패 시나리오로 공과 접촉하지 않은 닫기에서 미부착을 확인하고, 준비 timeout/요청 실패를 성공으로 오인하지 않는지 확인.
5. RViz를 켠 실행에서 공의 world object ↔ attached object 표시 전환과 로봇 상태를 선택적으로 시각 확인한다. 수행하지 않은 GUI 검증은 보고서에 명시한다.
6. 기존 `simulation.launch.py` 동작과 MoveIt standalone 계획 전용 실행(trajectory 실행 비활성 경계)을 회귀 확인한다.
7. `git diff --check`로 공백/패치 오류를 확인하고, 변경 파일 범위가 위 설계 목적에 한정됐는지 검토한다.

## 7. 구현 결과와 설계 대비 결정

- Gazebo Harmonic `ContactSensorData`로 양 손가락 충돌과 공 충돌을 확인하고, `DetachableJoint`로 `rg2_hand`와 공을 연결했다. 닫기 MoveIt action은 실제 접촉에서 취소하고 종료 상태를 확인한 다음에만 `/grasp/attach`를 호출한다. 제어 취소 직후 접촉이 풀릴 수 있어 **접촉 당시 두 관절 합이 5° 초과였다는 증거를 3초만 보존**하며, 부착 요청 시 현재 개방각도 재확인한다.
- `grasp_scene.py`는 Gazebo 전환 성공 뒤 MoveIt의 `apple`을 월드 ↔ 부착 물체로 전환하고, `GetPlanningScene`에서 ID·링크뿐 아니라 공 형상과 위치를 대조한다. 낙하 후 측정한 월드 위치도 다시 반영한다. 실제 Gazebo 바닥과 계획 장면의 간극을 막기 위해 `pick_area_floor` 충돌 물체를 초기 장면에 추가했다.
- 새 `pick_grasp_test.launch.py`는 기존 `simulation.launch.py`를 재사용한다. `grasp_test.py`가 준비, 빈손 음성 시험, 접근, 접촉·닫기 종료, 부착, 0.12 m 상승, 분리·낙하, Planning Scene 동기화를 검증한다. 바구니 이동은 여전히 5단계 범위다.
