# ros2_control 적용 3단계 실행 계획: 팔 키보드 명령 전환

상태: **3단계 구현 및 검증 완료.** 아래 계획에 따라 작업했고 결과를 문서 끝에 기록했다.

## 목표와 범위

`keyboard_joint_teleop`의 UR5 팔 명령을 관절별 Gazebo 브리지 토픽에서 `ros2_control`의 `/arm_position_controller/commands`로 전환한다. 기존 키 입력과 그리퍼 명령 방식은 유지한다. 이 문서는 원 계획의 3단계만 다루며, 4단계의 전체 통합 검증 완료를 선언하지 않는다.

기준 문서: 저장소 루트의 `ros2_control적용계획.md`. 현재 컨트롤러는 `forward_command_controller/ForwardCommandController`이며 `position` 인터페이스로 6개 관절을 받는다.

## 확정된 동작

| 입력 | 3단계 동작 |
| --- | --- |
| `1`~`6` | 기존 순서대로 선택 관절을 변경한다. 이 키만으로 명령을 발행하지 않는다. |
| `a` / `d` | 선택 관절의 **저장된 목표값**을 각각 `-0.05` / `+0.05` rad 변경하고 관절 제한 안으로 묶은 뒤, 팔 6개 목표값을 한 번에 발행한다. |
| `r` | 선택 관절의 목표값만 `0.0` rad로 바꾸고 팔 6개 목표값을 발행한다. 다른 관절 목표값은 유지한다. |
| `x` | 팔 6개 목표값을 모두 `0.0` rad로 바꾸어 발행하고, 기존 방식으로 그리퍼 목표값도 `0.0`으로 발행한다. |
| `o` / `c` | 기존 두 그리퍼 명령 토픽에 각각 `1.18` / `0.0`을 발행한다. 팔 목표값은 바꾸지 않는다. |
| 노드 시작 | 팔 목표값을 기존처럼 6개 모두 `0.0`으로 초기화한다. 컨트롤러 활성화가 확인된 뒤 초기 팔 목표값을 발행한다. 기존 그리퍼 초기 목표값 `0.0`도 발행한다. |

팔 명령은 `std_msgs/msg/Float64MultiArray`의 `data`에 다음 순서로 **항상 6개 값**을 담는다: `shoulder_pan_joint`, `shoulder_lift_joint`, `elbow_joint`, `wrist_1_joint`, `wrist_2_joint`, `wrist_3_joint`. 다른 5개 값은 마지막으로 명령한 목표값을 유지한다. 현재 코드의 관절 제한 `[-6.28319, 6.28319]` rad와 그리퍼 제한 `[0.0, 1.18]`을 유지한다. 실제 `/joint_states` 위치를 목표값 초기화나 키 증감의 기준으로 쓰지 않는다. 따라서 시뮬레이션의 최초 실제 자세와 `x` 이후의 0 rad 목표 자세가 다를 수 있다.

## 시작 순서와 오류 처리

`simulation.launch.py`는 `joint_state_broadcaster`가 성공한 다음 팔 컨트롤러 spawner를 시작한다. 키보드 노드는 별도 터미널에서 먼저 실행될 수도 있으므로, `/controller_manager/list_controllers`에서 `arm_position_controller`가 `active`인지 확인하고 나서 초기 팔 명령을 보낸다. 최대 대기 시간은 기존 spawner의 controller-manager 대기 시간과 같은 **120초**로 잡는다. 그 안에 활성화되지 않으면 명확한 오류를 출력하고 비정상 종료한다. 단순히 토픽 구독자 수만 확인하는 방식은 활성 상태의 증거로 쓰지 않는다.

기존처럼 시작 시 그리퍼 `0.0` 명령은 발행한다. 활성화 대기 중에는 키 입력 루프를 시작하지 않는다. 컨트롤러가 활성화된 뒤 초기 팔 명령을 한 번 발행하고 키 입력을 받는다. 이는 시작 명령을 활성화 전에 한 번만 보내서 잃는 상황을 막기 위한 순서다.

## 변경 대상과 순서

1. `my_arm_with_ball_application/scripts/keyboard_joint_teleop.py`: 팔 관절별 `Float64` publisher 6개를 팔 컨트롤러용 `Float64MultiArray` publisher 1개로 바꾼다. 팔 명령 함수는 저장된 6개 목표값 전체를 발행하도록 바꾸고, `a/d`, `r`, `x`, 시작 명령에서 호출한다. 그리퍼 publisher와 `o/c` 처리는 유지한다.
2. 같은 노드에 컨트롤러 활성화 대기를 추가한다. 120초 경과, 서비스 오류, 종료 신호의 처리와 터미널 설정 복구를 확인한다.
3. `my_arm_with_ball_application/package.xml`: 활성 상태 조회에 사용하는 ROS 인터페이스 패키지를 실행 의존성에 반영한다. 새 외부 라이브러리는 추가하지 않는다.
4. 3단계 동작에 직접 관련된 실행 안내만 필요하면 갱신한다. 기존 `docs/control_validation_checklist.md`의 `keyboard:=true` 예시는 현재 launch 인자와 맞지 않으므로, 이 문서를 실행 안내로 사용할 경우 별도 터미널 실행 방식으로 바로잡는다.
5. 원 계획의 3단계 체크박스는 아래 검증을 통과한 항목만 갱신한다. 4단계 체크박스는 4단계 통합 검증에서 판단한다.

`my_arm_with_ball_bringup/config/bridge.yaml`에는 현재 그리퍼 명령 브리지만 남아 있으므로 팔 브리지 삭제 작업은 추가로 없다. 컨트롤러 설정과 SDF/Xacro 제어 정의를 바꿀 계획도 없다.

## 검증 및 완료 조건

1. 변경한 애플리케이션 패키지를 빌드하고 관련 테스트 및 `colcon test-result --verbose` 결과를 확인한다. 키별 목표값 계산, 6개 값의 순서·길이, 제한값, `r/x`의 범위, 그리퍼 토픽 유지에 대한 집중 검증을 수행한다.
2. 시뮬레이션을 실행해 `ros2 control list_controllers`에서 `arm_position_controller`와 `joint_state_broadcaster`가 `active`인지 확인한다. 다른 터미널에서 키보드 노드를 실행한다.
3. 시작 시 `/arm_position_controller/commands`에 0 rad 여섯 값이 발행되는지 확인한다. `1`~`6` 선택과 `a/d`로 선택 관절 값만 `0.05` rad씩 변하는지, 제한을 넘지 않는지 확인한다.
4. `r`은 선택 관절만, `x`는 팔 전체와 그리퍼를 재설정하는지 확인한다. `o/c`의 기존 그리퍼 토픽과 동작을 확인한다. 팔의 실제 이동은 `/joint_states`로 확인한다.
5. 키보드 노드를 컨트롤러보다 먼저 시작하는 경우에도 활성화 후 초기 팔 명령이 전달되는지 확인한다. 컨트롤러가 활성화되지 않으면 120초 안에 오류를 알리고 종료하는지 확인한다.

완료 판정: 기존 키 조작으로 팔이 ros2_control을 통해 움직이고, 그리퍼 명령 경로가 유지되며, 초기 명령과 재설정 명령의 결과를 위 방법으로 확인한 경우에만 3단계를 완료로 표시한다. 실행 환경 문제로 시뮬레이션 확인을 못 하면 해당 검증 항목과 원인을 미완료로 기록한다.

## 실행 결과

- 전체 4개 패키지의 `colcon build`가 통과했다. `colcon test`와 `colcon test-result --verbose`는 3개 테스트, 실패 0건이었다.
- 헤드리스 Gazebo에서 두 컨트롤러가 `active`인 상태를 확인했다. 키보드 입력으로 6개 관절 각각의 명령·선택 관절 재설정, `x`의 팔 전체 재설정, `o/c`의 그리퍼 열림·닫힘을 확인했다. `/joint_states`에서 팔과 그리퍼의 실제 위치 변화를 확인했다.
- 키보드 노드를 Gazebo보다 먼저 실행했을 때 활성화 전에는 팔 명령이 발행되지 않았고, 활성화 후 여섯 개의 0 rad 초기 명령이 전달됐다. 서비스 미제공 시 대기 시간 만료 경로는 짧은 제한 시간을 준 자동 테스트로 확인했다.
- 빠른 연속 키 입력 검증 중 표준 입력 버퍼링으로 두 번째 키가 처리되지 않는 문제를 발견해 바이트 단위 입력으로 고쳤고 같은 시나리오를 다시 통과했다.
- 기본 `ament_flake8` 검사는 저장소의 기존 큰따옴표 스타일 등으로 통과하지 못했다. 변경 전 키보드 파일에서도 같은 검사에 29개 스타일 오류가 있었다. 구문·미정의 이름 등 핵심 검사(`flake8 --select E4,E7,E9,F`)와 `py_compile`은 통과했다.
