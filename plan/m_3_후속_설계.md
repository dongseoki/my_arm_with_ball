# MoveIt 적용 3단계 후속 설계 — 그리퍼 실행 연결

## 1. 목표

단계 3에서 검증한 팔 trajectory 실행 구조를 확장해, 단계 2의 SRDF `gripper` 그룹(두 finger joint)을 Gazebo ros2_control의 `FollowJointTrajectory` 액션에 연결한다. MoveIt에서 계획한 그리퍼 궤적을 Gazebo에 실행할 수 있게 하고, 키보드 `o/c`도 기존 열기·닫기 의미와 목표값을 유지하면서 새 그리퍼 trajectory action을 사용한다.

키보드 입력은 MoveIt 계획/충돌 검사를 우회해 controller action에 직접 전달한다. MoveIt 그룹 실행과 키보드 동작은 각각 검증하며, 둘 다 `/joint_states` 및 action 결과로 확인한다. **팔 또는 그리퍼 action이 진행 중이면 팔·그리퍼 키보드 입력을 모두 무시**한다(큐잉하지 않음). 접촉 감지, 공 부착/분리, 파지 성공 판정 및 전체 Pick-and-Place는 범위 밖이다.

## 2. 설계 범위와 기준

- 기존 SRDF의 `gripper` 그룹과 `rg2_finger_joint1`, `rg2_finger_joint2`를 재사용한다. 새 그룹이나 mimic 관계는 추가하지 않는다.
- `gripper_position_controller`를 두 finger joint용 `joint_trajectory_controller`로 교체한다. 동일 관절을 제어하는 위치 컨트롤러를 병행 활성화하지 않는다.
- 팔 및 그리퍼 controller는 서로 다른 joint command interface를 점유하며 통합 Gazebo launch에서 함께 활성화한다.
- MoveIt controller 설정에 그리퍼 컨트롤러의 `FollowJointTrajectory` endpoint와 두 관절 매핑을 추가한다.
- 키보드 `o/c`는 기존 목표값(`o = 1.18 rad`, `c = 0 rad`)을 보존한다. 각 목표의 두 관절 적용값·방향과 실제 모델 한계는 구현 및 Gazebo 검증에서 대조한다.
- 키보드 목표 궤적은 현재 `/joint_states` 값을 시작점으로 사용하고, action 성공과 별개로 실제 두 관절이 목표 허용 오차 내에 도달했는지 확인한다.
- 팔/그리퍼 action 중 모든 팔·그리퍼 조작 입력은 무시하고 기록한다. action 실패, 거부, timeout, 취소 및 상태 미도달은 구별해 보고한다. 자동 재시도는 하지 않는다.
- timeout 및 상태 허용 오차의 구체적 초기값은 기존 단계 3의 오류 처리 패턴과 모델/실측을 참고해 구현 시 정하고, 검증 결과와 함께 기록한다. 공 접촉·부착 관련 기준은 이 단계에서 정하지 않는다.
- standalone MoveIt 계획 데모의 실제 trajectory 실행 비활성화 경계를 유지한다.

## 4. 완료 기준

1. 통합 Gazebo 실행에서 joint state broadcaster, 팔 trajectory controller, 그리퍼 trajectory controller가 정상 활성화된다. 기존 `gripper_position_controller`는 같은 finger joint의 활성 제어 경로로 남지 않는다.
2. 팔과 그리퍼 controller는 각각 자신에게 할당된 관절만 점유하며 동시 활성화에 충돌이 없다.
3. MoveIt controller manager가 SRDF `gripper` 그룹을 그리퍼 `FollowJointTrajectory` action에 연결하고, MoveIt 계획·실행으로 Gazebo finger joint가 이동한다.
4. MoveIt standalone 계획 전용 실행은 이전처럼 실제 trajectory 실행을 허용하지 않는다.
5. 키보드 `o/c`가 기존 열기/닫기 의미 및 목표값을 보존해 gripper action을 보낸다. 목표값은 계획 모델의 관절 순서·한계 및 실측 이동 방향과 대조해 확인한다.
6. 키보드 action은 현재 관절 상태를 시작 상태로 사용하며, action 결과와 `/joint_states` 목표 도달 여부를 설정된 허용 오차로 각각 확인한다.
7. 팔 또는 그리퍼 동작 중 팔·그리퍼 입력 모두 무시되고 큐에 쌓이지 않는다. 동작 중 입력 무시 및 action 거부·실패·timeout·취소·상태 미도달이 로그에서 구별된다. 취소가 확정되기 전 새 키보드 action은 허용하지 않는다.
8. 자동 재시도가 없고 실패 뒤 노드가 안전한 입력 대기 상태로 복귀한다. controller/action 준비 실패 처리와 노드 종료 동작도 검증한다.
9. 관련 패키지 빌드, 테스트, lint가 통과하고 headless Gazebo 통합 실행에서 MoveIt 그리퍼 실행과 키보드 열기/닫기 상태를 재현해 확인한다. 시각 검증을 수행하지 않은 경우 이를 명시한다.
10. 접촉 감지, 공 부착/분리, 파지 성공 여부 판단 및 전체 Pick-and-Place 동작은 구현되지 않았으며 다음 작업 범위로 남는다.

## 5. 검증 계획

- SRDF·계획 모델의 그리퍼 그룹 관절 이름, 순서 및 한계를 ros2_control 설정과 대조한다.
- YAML/controller/MoveIt mapping 및 launch 구성의 일관성을 검사하고, 두 trajectory controller의 관절 소유권이 서로 겹치지 않는지 확인한다.
- 키보드 단위 테스트로 목표값, 입력 잠금의 양방향 동작, action lifecycle, 실제 상태 확인 및 오류 분기를 검증한다.
- `colcon build --symlink-install`, 관련 패키지 테스트 및 `colcon test-result --verbose`, lint를 실행한다.
- `simulation.launch.py headless:=true`에서 활성 controller와 action endpoint를 확인한다. MoveIt 그룹 계획/실행 및 키보드 `o/c`를 각각 실행한 뒤 `/joint_states`와 action 결과를 비교한다.
- standalone `demo.launch.py`에서 trajectory 실행이 비활성임을 회귀 확인한다.

## 6. 범위 밖 및 구현 시 확정할 값

- Gazebo 접촉 감지, 공 부착/분리, Planning Scene attached object 갱신 및 물리적 파지 성능
- Pick-and-Place 작업 노드, 놓기 판정, 자동 재시도
- 그리퍼 action의 timeout 및 관절별 허용 오차의 구체적 수치: 기존 단계 3 패턴과 실측 결과를 바탕으로 구현/검증 중 결정하고 결과에 기록한다.
- finger joint 방향·한계와 기존 `0`/`1.18 rad` 목표의 실제 동작 일치 여부: 코드에 값을 적용하기 전에 URDF/SDF 및 실행 상태로 확인한다.

## 7. 구현 및 검증 결과 (2026-10-14)

- `gripper_position_controller`를 `gripper_trajectory_controller`로 교체하고, MoveIt controller manager에 `gripper` 그룹 두 관절의 `FollowJointTrajectory` 매핑을 추가했다. 기존 팔 controller와 standalone 계획 전용 demo의 실행 제한은 유지했다.
- 키보드 `o/c`는 현재 두 finger joint의 `/joint_states`를 시작점으로 하는 trajectory action을 보낸다. 팔·그리퍼 action은 하나의 busy 상태를 공유하며, 실행 중 양쪽 조작 입력을 모두 무시한다. action 결과와 별도로 최종 관절 오차 `0.01 rad`를 확인한다. 기본 실행 시간은 최대 관절 이동량 / `0.2 rad/s`와 최소 `1.0 s` 중 큰 값이며, action timeout은 그 시간 + controller goal 시간 허용 `2.0 s` + 여유 `2.0 s`다.
- 전체 workspace `colcon build --symlink-install` 및 `colcon test`/`colcon test-result --verbose` 통과: 5개 패키지 빌드, 3개 테스트·실패 0. 키보드 단위 테스트는 25개 통과했으며 실제 SIGINT/SIGTERM 경로의 종료 전 취소 회귀 테스트를 포함한다. YAML 관절 매핑·소유권 검사, Python 구문 검사, `git diff --check`도 통과했다.
- 기존에 실행 중이던 별도 시뮬레이션과 충돌하지 않도록 `ROS_DOMAIN_ID=93` 및 별도 `GZ_PARTITION`에서 `simulation.launch.py headless:=true rviz:=false`를 실행했다. `joint_state_broadcaster`, 팔·그리퍼 trajectory controller가 모두 `active`였고 두 finger 및 팔 6개 position command interface가 각각 점유됐다. MoveIt 로그에서 두 action controller 등록을 확인했다.
- MoveIt `gripper` 그룹은 열림 `1.18 rad` 및 닫힘 `0 rad` 목표를 각각 계획·실행했다. 각 계획은 92개 궤적점, 실행 action 결과 `SUCCESS`였으며 `/joint_states`는 열림 `[1.17849, 1.17853] rad`, 닫힘 `[0.00156, 0.00154] rad`로 두 관절 모두 `0.01 rad` 이내였다.
- 키보드 action 경로도 실제 Gazebo에서 `o/c`를 실행했다. 측정 열림 `[1.17332, 1.17332] rad`, 닫힘 `[0.00832, 0.00832] rad`로 허용 오차 이내였다. 그리퍼 실행 중 팔 입력, 팔 실행 중 그리퍼 입력이 각각 무시됐고, 팔의 `+0.05 rad` 실행도 목표 오차 `0.0050 rad`로 확인했다.
- 독립 `demo.launch.py use_rviz:=false`에서 `allow_trajectory_execution=False` 및 `/execute_trajectory` action 부재를 확인했다.
- 검증 한계: GUI/RViz 시각 확인은 하지 않았다. timeout·취소·거부·상태 미도달은 단위 테스트로 검증했으며, Gazebo에서 의도적인 stall을 만들어 해당 실패 경로를 재현하지 않았다. 접촉·공 부착/분리는 여전히 다음 단계 범위다.
- 직접 실행한 `ament_flake8`는 기존 파일 전반의 `I100`(import 순서)·`Q000`(큰따옴표) 스타일 위반으로 통과하지 못했다. 기능 관련 `flake8 --select=E,F --max-line-length=99`는 통과했고, `colcon test`에 구성된 검사도 통과했다. 대규모 스타일 변경은 이번 기능 범위에 포함하지 않았다.
